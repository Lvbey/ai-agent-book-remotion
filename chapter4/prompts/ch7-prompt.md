## 3. 这一章的讲解重点（拍板，别自行发挥）

1. **全章的主论点只有一句：评估的对象不是模型，是「模型 + Harness 的组合体」。**
   每一节都要能回到这句话。这句话是本章区别于"跑个 benchmark"的全部价值。
2. **7.1 必须讲清"三件套"**：任务定义、环境（能不能真的操作）、评分器（怎么判断成功）。
   τ²-bench 那条真实的 telecom 任务是全章最好的具体样本，让读者从一条 JSON 看懂评估长什么样，
   后面所有抽象讨论都靠这一页兜底。
3. **7.2 的 Pass@k 与 Pass^k 是全章最反直觉、最该被记住的一页。** 原文那个 p=0.6、k=5 的算例
   （Pass@5≈99%，Pass^5≈7.8%）必须原样保留并做成视觉对比——传统开发人员看到这两个数字才会
   真正理解"演示能跑"和"能上生产"差在哪。**这一页至少给两屏。**
4. **7.4 别写成"讲怎么写测试用例"。** 传统开发人员会用单元测试的直觉去理解，要明确说清差别：
   评估集的分布要对应真实任务、要防泄漏、任务要从失败中长出来。
5. **7.5.1 LLM-as-Judge 最容易写成"让 GPT 打个分"**。必须讲清判官的偏差（位置、长度、
   自我偏好）和校准手段，否则读者会照着一个会骗人的判官建整套评估。
6. **7.7 只有 25 行，很多人会顺手删——不许删。** 它回答的是"分数涨 2 分到底算不算涨"，
   是整章唯一的统计学刹车。给 3 页，把置信区间和配对比较讲清楚，公式保留但要说人话。
7. **7.8 可观测性只有 20 行，同理不许删**，压成 3 页也要在。
8. **模型替换实验 vs 消融实验是两把不同的刀**（开头就点明了）：前者区分"瓶颈在模型还是在 Harness"，
   后者定位"Harness 里哪个部件重要"。找一页把两者并排对照，这是读者最容易混淆的一对概念。

## 4. 硬性约束（第 5 章验证过，别改）

- **只用骨架已有的 CSS 类，不改 CSS / JS。** 微调用行内 `style`，只允许
  `margin` / `padding` / `max-width` / `font-size`。
- 一页一个结论，标题写成一句**能被反驳的话**，不写"评估指标"这种目录式标题。
- 卡片正文 ≤3 行，导语 ≤2 行，一页 ≤1 个 `.note`。
- 中文全角括号词组不许跨行断开（整组包 `<span class="nw">` 或手写 `<br>`）。
- 内容块 `max-width` 要么不写（吃满 1124 版心），要么显式对齐，**不许写 1020 这类数**。
- 作者写"这个判断有边界 / 这里不适用"的段落一个都不能删，压成 `.note`。
- 零外链。表格、流程图、公式示意一律手写 SVG 或 HTML，不引图片。
- **原文是带公式的 epub 转出来的，`kk` / `nn` / `pp` 这类重复字母是渲染残留，要还原成单个
  `k` / `n` / `p`。** 公式本身要保留，但旁边必须有一句人话解释它在说什么。
- 中文引号用「」，**不要写脚本批量替换**（会连带改坏 CSS 和 JS，见 `references/qa-and-pitfalls.md` 坑 2）。
