## 3. 这一章的讲解重点（拍板，别自行发挥）

1. **全章最锋利的一句话是"保存经历不等于从经历中学习"。** 要放在最靠前的位置（章首那几页里），
   并且在 9.1 和 9.3 各回收一次。读者如果只记住一句，就记这句：写日志那一刻什么都没学到，
   学习发生在系统主动完成"评价、对照、归纳、验证"之后。
2. **"为什么不让模型每次任务后直接训练自己"这段刹车必须完整保留。** 原文给了四条理由：
   生产环境的学习信号不干净、局部更新会造成能力遗忘/策略漂移/安全退化、未经验证的反馈会把
   错误经验和提示注入固化下来、基础模型的周期训练吸收不了私有经验。这是全章最容易被删、
   也最有价值的部分——删了读者会得出"那就让它自己训练"的错误结论。给它一整页 `.note`。
3. **四种方法不是并列的四选一，是一条"改动范围递增"的阶梯**：知识 → 指令 → 程序 → 参数。
   顺序本身就是论点（能往外放就别往里改）。9.2 引子那张总表必须做成页内主角，
   后面 9.2.1–9.2.4 每讲一种都回到这张表的同一行。
4. **9.2.5 是元层面，最容易被写丢**："从更新产物到更新'更新方法'"。它是"持续进化"和
   "攒了一堆 Skill"的分水岭，给 3 页，别塞进 9.2.3 里带过。
5. **9.3 的双循环结构是全章的工程落点**：在线执行循环只干活、只记录，不直接改正式 Agent；
   离线进化循环聚合轨迹、诊断根因、生成提案，过验证门槛才发布新版本，两者靠版本化的
   经验库和评估集连接。**这一张图必须画准**，画错了整章就散了。
6. **Voyager 的三个机制（自动课程 / 技能库 / 迭代提示）原文特别强调了"缺一不可"**，
   用一张三缺一的对照图比三段文字有效得多：只有技能库没有课程 → 不知道下一步学什么；
   只有反思没有环境验证 → 技能库积累错误；只有探索没有持久化 → 每次从头开始。
7. **harness-updating 与 harness-benefit 的区分非常值钱，别漏**：一个是"能不能产生好的修改"，
   另一个是"任务模型能不能在后续找到并正确用上这些修改"。原文特别指出**不能只用端到端分数
   反推更新器好坏**——这句话要单独成页，它是"我明明加了 Skill 却没变好"的答案。

## 4. 硬性约束（第 5 章验证过，别改）

- **只用骨架已有的 CSS 类，不改 CSS / JS。** 微调用行内 `style`，只允许
  `margin` / `padding` / `max-width` / `font-size`。
- 一页一个结论，标题写成一句**能被反驳的话**，不写"四种进化方法"这种目录式标题。
- 卡片正文 ≤3 行，导语 ≤2 行，一页 ≤1 个 `.note`。
- 中文全角括号词组不许跨行断开（整组包 `<span class="nw">` 或手写 `<br>`）。
- 内容块 `max-width` 要么不写（吃满 1124 版心），要么显式对齐，**不许写 1020 这类数**。
- 零外链。双循环图、四阶梯图、Voyager 三机制图一律手写 SVG。
- 原文里的表格（表9-2 四种方式对比、表9-3 分层评估指标）**要保留成真正的表格**，不要拆成卡片。
- 中文引号用「」，**不要写脚本批量替换**（会改坏 CSS/JS，见 `references/qa-and-pitfalls.md` 坑 2）。
