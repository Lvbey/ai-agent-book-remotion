## 3. 这一章的讲解重点（拍板，别自行发挥）

1. **全章的总开关只有一条，在 10.2：协作过程是否引入了单个 Agent 在生成时无法获得的新信息。**
   这一条要放在最靠前的位置立住，后面每讲一个模式都回来问一次。它能把读者脑子里 80% 的
   "我们上多 Agent 吧"直接劝退——这才是本章对工程决策的真实价值。
   10.2 那张"各模式是否引入新信息"的表必须做成页内主角。
2. **章首的"群体智能可以高于个体"是愿景，10.2 是刹车，两者要并置。** 先讲为什么值得做
   （否则读者觉得整章没必要），紧接着讲什么时候不该做（否则读者回去就开干）。
   这两个基调在同一屏前后脚出现，效果最好。
3. **10.1 的两个维度（上下文是否共享、谁来协调）是后文全部结构的索引。** 这一页要画成
   二维图，后面 10.3 / 10.4.4 / 10.4.5 每一节开篇都能在这张图上点亮一格。
4. **10.4.3 的五个对等模式（Loop 工程 / 提议者-审核者 / 辩论 / 头脑风暴 / 专家小组）
   千万不要做成五张并列卡片**——那样读者看完还是不知道该用哪个。必须有一张
   "问题长什么样 → 用哪个模式"的选择表，五个模式各自只留一句它解决的问题。
5. **10.4.4 管理者模式是全章最大的单块（164 行），也是工业界最常用的形态，给足 10 页。**
   它跟 10.4.5 去中心化的对比要明确：中心化好在可预测、可审计，差在单点；去中心化反之。
   这一对对照要让读者能直接回答"我们团队该选哪个"。
6. **10.5 失败模式是全章最该被读完的一节，不许压缩。** 有三件事必须讲到：
   - 14 种失败模式归成三类（系统设计缺陷 / Agent 间对齐失败 / 任务验证缺失）；
   - **修修补补没用**——原文给了"即使采用简单修复，效果也十分有限（ChatDev 仅提升 15.6%）"，
     并把它们定性为架构级缺陷而非工程 bug，这句判断要原样保留；
   - **拜占庭故障这个类比是本节最值钱的一句**：传统分布式系统大多只需防"部件停了"，
     而 Agent 的故障天生是拜占庭式的——它很少停下，而是继续给出看起来可信的错误结论，
     而且不会声明自己是错的。这解释了为什么本章到处是交叉验证和多数表决。
7. **10.6 Agent 社会（6 个案例、150 行）最容易做成新闻摘要堆砌。** 硬要求：
   **每个案例只回答"它证明了什么"**，一页最多两个案例，删掉所有背景介绍和数字细节。
   这一节的作用是让读者看见集体智能的上限，不是科普。案例之间要有一条递进线：
   社会模拟 → 长期生活 → 社交网络 → 经济竞争 → 真实经济中的交易 → 信息不对称下的博弈。
8. **凡是原文给的"这么做没用 / 边界在哪里"的判断，一个都不许删。** 本章这类刹车特别多，
   删掉任何一条，读者都会做出过度设计。

## 4. 硬性约束（第 5 章验证过，别改）

- **只用骨架已有的 CSS 类，不改 CSS / JS。** 微调用行内 `style`，只允许
  `margin` / `padding` / `max-width` / `font-size`。
- 一页一个结论，标题写成一句**能被反驳的话**，不写"多 Agent 的分类"这种目录式标题。
- 卡片正文 ≤3 行，导语 ≤2 行，一页 ≤1 个 `.note`。
- 中文全角括号词组不许跨行断开（整组包 `<span class="nw">` 或手写 `<br>`）。
- 内容块 `max-width` 要么不写（吃满 1124 版心），要么显式对齐，**不许写 1020 这类数**。
- 零外链。二维分类图、中心化/去中心化对照图、协作拓扑图一律手写 SVG。
- 原文的表（表10-1 信息增量对比）要保留成真正的表格，不要拆成卡片。
- 中文引号用「」，**不要写脚本批量替换**（会改坏 CSS/JS，见 `references/qa-and-pitfalls.md` 坑 2）。
