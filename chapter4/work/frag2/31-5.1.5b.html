5.1.5 · 恢复/按对用户透明的程度分级

能用低一级的手段，就不要升级

分完类、计完数，才轮到「怎么救」。三级手段按对用户透明的程度排列， 判断标准只有一条：这一级能不能自己把问题吃掉。

01

静默重试

同一个请求，退避之后再发，对用户完全不可见。升级条件：重试用尽仍失败。

02

降级与接续

改变请求本身再试：提上限、换模型、换模式。升级条件：怎么改都不通。

03

暴露给用户

所有自动手段用尽，才呈现错误并附上已尝试的动作。这里没有下一级。

VISIBILITY · 用户视角
# 用户能感知到哪一层 L1 静默重试 （看不见） L2 降级 · 接续 （看不见） —— 以上都在扣留错误 —— L3 暴露错误 一条完整说明 # 越往下，代价越高 # 时间 → 请求 → 用户重新理解
SUMMARY分级的意义

大多数故障停在第一级，第二级是例外，第三级是兜底

每升一级，代价就翻一倍：第一级只花时间，第二级要改请求，第三级要用户重新理解任务。

5.1.5 · 静默重试/两个细节决定成败

「失败就重试」有两个坑

同样是重试，退避策略没做对会制造二次拥塞；调用优先级没分清， 后台重试会挤占主链路的配额。

RETRY POLICY · 退避与抖动
# 两个细节都在这几行里 for attempt in 1..N: if not retryable(err): break wait = min(cap, base * 2 ** attempt) wait += random(0, jitter) # 抖动 if err.retry_after: # 服务端提示 wait = max(wait, err.retry_after) sleep(wait)
  • 抖动不是装饰。纯指数退避会让所有客户端在同一毫秒发起第 N 次重试；随机抖动把这一批打散，否则重试本身就是一次小型 DDoS。
  • 服务端说了算。返回里带等待时长时，就按它来——那是对方最清楚自己什么时候能缓过来的时刻。
  • 前台重试，后台放弃。主循环的请求失败要重试；标题生成、输入建议这类辅助调用失败直接丢掉。后台重试挤占的是主链路的配额，这叫重试放大。
重试放大的可怕之处：它不报错。用户只会觉得「今天这个 Agent 有点慢」， 而账单和限流额度已经在后台被一堆没人看的标题消耗掉了。
5.1.5 · 降级与接续/改请求本身再试

重试无效，说明问题不在「什么时候发」

而在「发什么」。这一级的动作是改变请求的形状：改上限、改模型、改模式——三个最常见的场景。

01输出触顶

被长度限制截断OUTPUT TRUNCATED

先静默提高输出上限重发；仍不够，就在消息末尾追加一条元指令，让模型从断点接着往下写。

02主模型过载

降级到备用模型FAILOVER

但先剥离旧模型私有的格式块——否则新模型解析不了历史消息，降级当场失败。

03成本模式

高成本模式被限流RATE LIMITED

暂时回落到标准模式。先用可接受的答案把这一轮跑完，质量优化留到配额恢复之后。

三件事的共同点：改的不是重试次数，是请求本身。 所以这一级必须知道「这次失败到底缺什么」——只看到 429 就降模型，等于用更大的代价换一个不相干的答案。

顺序不能反：先提上限再谈接续，先剥格式再谈换模型。 跳过前置条件直接降级，是把一次可恢复的失败变成一次不可解析的失败。
5.1.5 · 最后一级/所有自动手段用尽之后

最后一步，才是让用户看见

不是一句「出错了」，而是一份交接单：我试过什么、走到哪一步、你接手时能从哪儿继续。

ERROR · 呈现给用户的样子
任务未完成：修改 src/db.py 时连接超时 # 已尝试的恢复（按顺序） 1. 静默重试 3 次 · 指数退避 2. 降级到备用模型 3. 压缩上下文后重发 ✓ 4. 跨厂商接管 ✗ # 建议的下一步 - 文件较大，可拆成两次编辑 - 或先只读，产出一份补丁
  • 位置。明确停在第几步，而不是笼统的「失败了」——用户才知道该从哪儿重来。
  • 动作。列出已经试过的恢复路径，避免用户重复你已经做过的事，也避免他误以为你没试。
  • 出口。至少给一条可执行的下一步：拆小任务、换模式、只读产出补丁。
前两级对用户完全不可见。这不是体验打磨，而是「恢复期间扣留错误」这条工程纪律的直接结果—— 下一页把它讲成一条通用原则。
5.1.5 · 工具层/错误变成模型的输入

工具层错误不终止会话

幻觉调用、参数不合法、执行抛异常——这些错误若抛给用户，任务就死在这里； 喂回给模型，下一轮还有机会自己改。

TOOL RESULT · 错误也是结果
# 模型幻觉调用了一个不存在的工具 工具返回 { "ok": false, "error": "tool_not_found", "tool": "read_dir", "available": ["read","write","edit", "glob","grep","bash"] } # 它和正常结果没有区别 # 只是 content 里的一段 JSON
  • 幻觉调用。收到「工具不存在」的结构化结果，并附上真实可用的工具清单——它下一轮就知道该用哪个。
  • 参数校验失败。错误里带上输入约束：哪个字段、什么类型、取值范围。只说「参数错误」等于没说。
  • 畸形参数。本该是对象却给了字符串，这类在执行前先做程序化修复，修不好才作为错误返回。
这是「反馈越结构化越好」的直接应用：喂回的错误越具体，模型自我纠正的成功率越高； 一句「调用失败」，只会让它把同一个错误再犯一次。
5.1.5 · 核心原则/边界是整个恢复循环

错误处理的边界不是单次请求

是整个恢复循环。在确认无法恢复之前，中间错误不该让消费者看见——无论是用户，还是订阅事件的下游系统。

这就是第一章那条纠正原则的工程化：在确认无法恢复之前，不暴露中间态。 恢复成功，消费者毫无感知；全部失败，才统一呈现一次。
5.1.5 · 跨厂商接管/把没跑完的轨迹交给另一家

能带走的是文字，带不走的是凭证

主模型持续不可用时，要换一家把这条轨迹接着跑完。障碍不在接口地址， 而在轨迹里有一部分东西只属于原厂商。

THOUGHT · 一段思考的两个部分
[thought] text 「先读 package.json 看脚本」 signature 厂商签发的凭证 ✗ 换家即失效 [tool_call] name read args {"path": "package.json"} [tool_result] ref call #1 # 工具调用：结构不同，语义一致 # 按目标厂商重新渲染即可
  • 工具调用好办。各家字段名不同、嵌套不同，但「调了什么、参数是什么」的语义一致，重渲染就行。
  • 难办的是思考。它由可读的文字与厂商附上的凭证构成——凭证用来证明这段思考确实出自它自己。
  • 换一家，文字照读，凭证作废。这就是接管的可行边界：搬得动的是内容，搬不动的是身份。
一句话记住：跨厂商接管的边界，就是「可移植的文字」与「不可移植的凭证」之间那条线。 后面所有的工程动作，都是在这条线的两侧做取舍。
5.1.5 · 凭证/三家三种态度

各家要求不同，方案按最严的一端设计

从「根本不校验」到「拒绝一切非自己签发的」，中间还有把凭证挂在工具调用上的——同一份轨迹，三种反应。

接收端对凭证的态度你的对策
宽松 不做校验，思考与凭证都照收 直传能过，但别把它当成通用方案
中等 校验签发方，外来凭证一律不认 丢弃凭证，文字以普通内容身份带入
严格 凭证还挂在工具调用上，删思考不管用 把历史调用改写成文字叙述，只求能接着跑

所以「把思考删干净就安全了」这条看似稳妥的策略，在严格的一端反而通不过—— 它删的是文字，凭证还在调用上。

退路要提前想好：历史工具调用改写成文字叙述后，模型不再把它当作真正调用过的工具， 但它至少能接着往下跑——这就是「降级到能跑」，而不是「保证无损」。
5.1.5 · 中立格式/可移植的留下，不可移植的标出来

轨迹不该按任何一家的接口格式存储

既然换厂商时必然要重写一遍，不如一开始就存成中立的——四种字段，一条原则。

NEUTRAL · 一条中立记录
{ "role": "assistant", "thought": { "text": "先读 package.json", "sig": null # 切换时丢弃 }, "calls": [ {"name": "read", "args": {"path": "package.json"}} ] } # 标识符在渲染成请求时才生成
  • 思考拆两半。文字是可移植的，凭证不是——存的时候分开，切换时只丢后半。
  • 调用只记名称与参数。不记厂商的 call id，标识符在渲染成具体请求时按目标厂商重新生成。
  • 文字当普通内容带入。不塞回目标厂商放思考的位置——那不是它的思考，它会拒绝。
  • 摘要本来就是副本。厂商返回的思考摘要，正是为这种场合准备的可移植版本，留着即可。
它的价值不止故障切换：第七章的评估重放、第八章的训练样本构造、第九章的经验提取， 依赖的都是同一份产物——中立格式是这套系统的公共底座。
5.1.5 · 实验 5-1/难度 ★★★

实验 5-1：换一家，把没跑完的轨迹接着跑

目标：验证中立格式能否让跑到一半的 Agent 换一家接着跑完，并量化「原样直传」与「一刀切剥光」的代价。

01设置

在哪儿切换SETUP

任务需多轮工具调用；中途注入连续的限流与过载，熔断后切换。选三家线上格式互不相同的厂商，两两切换。

02对照

三种做法METHODS

直传原样搬进新结构；剥离删掉全部思考与凭证；中立丢凭证、留文字，标识符按目标重渲染。

03验收

拿什么比METRICS

首个请求留原始响应，失败必须是厂商真实报错。比完成率、切换后重复调用同一工具的次数、额外轮数与 token。

三种做法的差别只在「换手时丢掉什么」：直传丢零样、剥离丢全部、中立只丢凭证。 其余变量——任务、断点位置、目标厂商——必须完全一致，否则数字没有意义。

验收里有一条逆向要求：若中立做法在「重复调用」上并未优于剥离，同样如实记录。 实验的职责是给数，不是证明观点。
5.1.5 · 实验 5-2/难度 ★★

实验 5-2：输出断在一半，怎么接

目标：比较「整轮重发」与「以半截输出为前缀续写」，在成本、正确性与副作用上差多少。

01断点

切在三个位置BREAKPOINTS

在流式响应上分别切断：思考中途、正文中途、工具调用参数中途。三个位置坏的形状完全不同。

02三种接法

怎么续RECOVERIES

丢弃整轮重发；半截作为末尾 assistant 消息要求接着写；追加元指令说明从断点继续。半截调用要先转成文字再补完。

03验收

记四个数METRICS

恢复成功率、相对整轮重发省下的输出 token、补完后参数的合法率与语义正确率、重复副作用次数。

前三项是成本账，第四项是安全账：省下来的 token 一旦换来一次重复执行，就是负收益。

判分点在最后两项：合法不等于正确——拼接处常多出空白或重复字符； 而重复副作用，一次就够毁掉整轮结果。续写前按「工具名 + 参数」指纹去重。
5.1.5 · 熔断/每条恢复路径都要有上限

阈值从生产数据来，不靠拍脑袋

恢复机制自己也会失效，所以每条路径都要封顶。上限设成几，不该由直觉决定。

01上下文

压缩封顶COMPACTION

连续失败若干次就放弃压缩，改用硬截断。继续压缩只会把上下文越压越坏。

02权限

分类封顶PERMISSION

权限分类连续失败，就回退到人工询问。分类器不确定时，问人比猜便宜。

03输出

接续封顶CONTINUATION

续写最多尝试固定轮数，到点停手，把半截结果交出去。续到第 N 轮还断，说明接续解不了。

THRESHOLD这个「3」从哪来

连续 3 次CLAUDE CODE · 上下文压缩熔断

真实会话统计：曾有一个会话在这条路径上连续失败三千余次；这类无效重试每天在全球浪费约 25 万次 API 调用，逾千个会话出现过 50 次以上连续失败。

3 次是拐点，不是最优解：它落在「绝大多数故障在此之前已恢复」与「继续重试基本无望」之间—— 有数据支撑的解，比拍脑袋的解更容易在下一次事故里被辩护。
5.1.5 · 终止/单点熔断之外，还有连锁

死亡螺旋：恢复逻辑自己也会故障

单点熔断管一条路径的失败次数；死亡螺旋管的是路径之间——恢复动作触发的错误，又去触发同一个恢复动作。

01

上下文溢出，Agent 停止

这一轮已经跑不动了。

02

停止钩子被触发

「结束时自动提交代码」——结束时自动执行的清理逻辑。

03

钩子调用 LLM 写 commit message

本来只是补一句说明。

04

又撑爆上下文，再次触发钩子

回到第 01 步。这一次没人叫停。

01切断源头

错误路径上禁用副作用

一切会再次调用模型的逻辑都停掉。宁可丢掉一次辅助功能，比如自动记忆提取——它不是这轮任务的一部分。

02打断残余

递归深度计数器

检测并打断残余的连锁：已经在恢复里了，就不要再进入恢复。深度是唯一不会说谎的信号。

最后还有一层全局兜底：最大迭代轮数、会话预算上限、连续失败超阈值时升级人工干预—— 单点熔断管单条路径，全局条件管整个会话。
