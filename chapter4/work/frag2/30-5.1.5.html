5.1.5 · 故障与错误恢复/三个问题，一条线索

故障恢复，才是真正的分水岭

上一节给的是原则与组件；这一节把它们放进真实故障里跑一遍。 三个问题，顺序不能换：先分类，再检测，最后才谈恢复与终止。

Q1分类

会遇到哪些故障

API、工具、上下文、控制流四层。层不同，处置手段完全不同——不能都用一句「重试一下」打发。

Q2检测

怎么发现它坏了

单次错误只看类型；真正该盯的是重复调用指纹与连续失败次数——那是行为出了问题。

Q3终止

什么时候必须放手

恢复机制自己也会失效。每条恢复路径都要有上限，「什么时候停」和「怎么救」同样重要。

问题的严重性，第一章已经演示过：仅仅缺失一条工具结果反馈，就足以让 Agent 陷入无限循环。 真实生产里的故障只会更多样，所以这一节从分类讲起。
5.1.5 · 故障分类学/先分类，再谈处置

按发生的位置，把故障切成四层

这是系统应对的第一步。分类不是为了归档，而是为了选手段——同一句「重试一下」，在四层里的含义完全不同。

L1基础设施

API 层API LAYER

限流、过载、超时、断连、输出截断。任务可能完全正确，是基础设施在报错。

L2手脚

工具层TOOL LAYER

幻觉调用、参数畸形、执行抛异常。错在Agent 伸出去的那只手。

L3记忆

上下文层CONTEXT LAYER

窗口溢出、压缩失败、轨迹结构损坏。错在喂给模型的那段历史。

L4循环

控制流层CONTROL LAYER

死循环与死亡螺旋。错在Agent 自己的下一步，外部环境其实正常。

分层的用处很直接：前两层多半靠「等」或「改输入」，后两层必须靠「打断」。 把四层混成一类，就只能一律重试——而重试恰恰救不了后两层。
5.1.5 · API 层/与任务内容无关

API 层的故障，不说明任务做错了什么

它只说明「这一次请求没被服务好」。所以在这一层里改任务、改提示词，都是无效动作。

API LAYER · 五种噪声
429 Too Many Requests ← 配额用尽 503 Service Unavailable ← 上游过载 — request timeout ← 链路太慢 — connection reset ← 连接被掐断 — finish_reason=length ← 输出触顶 # 任务没变、提示词没变，重发还是同样的结果
  • 共同点：与任务内容无关。换一个任务、换一句提示词，这些错误照样出现。
  • 所以有效的动作只有两个：等（退避之后再来），或者改请求（上限、模型、区域）。
  • 但「可重试」不等于「原样重试」。输出触顶也能再发，前提是先把上限提高，或从断点接续。
把它当噪声，还有个隐性好处：不用去怀疑模型的判断——在错误的地方调提示词，是最常见的排查浪费。
5.1.5 · 工具层/三种畸形，一种循环

三种单次事故，和一种行为模式

前三种错在「这一次调用」，装成工具结果喂回去，模型下一轮就能自己改； 最后一种错在「反复做同一件事」。

01幻觉

幻觉调用HALLUCINATED CALL

调用了不存在的工具。错不在参数，在它以为这个工具存在。

02约束

参数畸形MALFORMED ARGS

不符合输入约束——该给对象，却给了字符串。模型知道要做什么，只是写错了。

03运行

执行抛异常EXECUTION ERROR

工具真的跑了，但中途失败。以上三种，都可以装成一条工具结果返回。

04最危险

同错重试RETRY LOOP

工具反复返回同一个错误，模型不加改变地反复重试。这不是事故，是行为模式。

两类故障，两种治法：单次事故靠「更具体的错误信息」就能治； 行为模式不行——错误早就返回了，模型只是没改，它需要的是计数器，而不是再重试一次。
5.1.5 · 后两层/错在 Agent 自己

后两层不是环境坏了，是 Agent 自己坏了

请求发得出去，工具也跑得动。坏的是它对历史的记忆，和对下一步的选择——外部一切正常，对话却已经走不下去。

L3记忆

上下文层CONTEXT LAYER

窗口溢出、压缩失败、轨迹结构损坏——比如工具调用缺少配对的结果消息。错在「模型看到的历史」，不在模型本身。

L4循环

控制流层CONTROL LAYER

死循环是反复执行相同操作却毫无进展；死亡螺旋是恢复逻辑自己又调 LLM、再次出错、连锁反应。错在「Agent 的下一步」。

COMMON处置方式

共同点：越「努力」越糟——所以不能等，只能打断

前两层还能换一种输入来修；后两层继续跑下去，只会烧掉更多 token，把错误固化成更大的错误。

这就是分类的价值：同样是「失败了」，L1 该退避、L2 该改参数、L3 该压缩或修复轨迹、L4 该直接终止这条路径。
5.1.5 · 检测/先判断值不值得

先问「值不值得」，再决定怎么重试

捕获故障后的第一个判断，不是「要不要重试」，而是「原样重发，会不会得到不同结果」。

捕获到的故障可重试？该做什么
限流 429 · 服务过载 · 网络抖动 可重试 同一个请求，退避之后再发——退避要叠加随机抖动。
输出触顶被截断 可重试，但请求要变 先提高输出上限；仍不够，就在末尾追加元指令从断点接续。
参数不合法 · 参数畸形 不可重试 原样重发多少次都是同样结果，必须改输入。
权限不足 · 工具不存在 不可重试 改策略：升级人工，或把结构化错误喂回给模型。
所以生产级 Harness 维护的是一张「错误 → 恢复策略」映射表，而不是一句笼统的「出错就重试」。 可重试与不可重试的分界线，就是「重发会不会有信息增量」。
5.1.5 · 检测模式/单次之外看模式

比单次错误更该盯的，是重复出现的模式

单次错误告诉你「哪里坏了」；重复出现的模式才告诉你「它已经修不好了」。 两个计数器，盯的都是后者。

01指纹

重复调用指纹CALL FINGERPRINT

对「工具名 + 参数」算指纹。同一指纹反复出现，说明它在原地打转——第一章消融实验里反复调同一工具，正是这个模式。

02计数

连续失败计数FAILURE COUNTER

每条恢复路径各记一本账：压缩、权限询问、输出接续分别计数。混在一起，一条路径的问题会污染另一条的判断。

03去处

为熔断提供依据CIRCUIT BREAKER

计数不是为了统计，是为了在「再试也没用」那一刻之前停手。阈值一到就掐断这条路径，把配额留给别的办法。

这两个机制都不需要模型参与：它们跑在 Harness 里——所以模型「觉得自己还在努力」的时候，外面已经能判定它卡住了。
5.1.5 · 活性监控/连接在，数据不来

最危险的失败不是断开，是静默卡死

断开至少会立刻报错；静默卡死不会——连接建立成功，数据流却停了，像水管通着但不出水。

STREAM · 连接正常，数据停了
[00:00] connect 200 OK ✓ [00:01] chunk 「分析这个…」 ✓ [00:02] chunk 「仓库的…」 ✓ [00:47] — 无新字节 ? [00:48] sdk timeout — ✗ 不触发 [00:49] watchdog idle > 20s ✓ 判定卡死 [00:50] kill stream → 触发重试
  • SDK 的超时往往只管建连。连上之后就不再计时，传输停住它也不会报错。
  • 所以要独立的空闲看门狗（watchdog timer，超过设定时间没有新输出就判定卡死），而不是复用连接超时。
  • 超时之后要主动杀死挂起的流，再触发重试。挂着的流不释放，重试只会让并发越叠越高。
可推广成一条原则：每个长连接都需要活性信号，而不能只依赖连接超时。
5.1.5 · 完整性监控/结构坏了，先修再喂

轨迹缺了配对，要在注入之前补好

工具调用必须有配对的结果消息；缺了，模型看到的就是一段自相矛盾的历史。 修复发生在注入上下文之前，而不是把结构异常抛给模型或用户。

MODE 01产品

产品模式PRODUCT · 宽容

缺哪条结果，就补一条占位消息，让轨迹保持结构完整。用户不该因为一个内部结构问题被打断。

MODE 02训练

训练数据收集TRAINING · 严格

拒绝修复：合成占位符会污染训练数据——模型会学到「结果可以是编的」。宁可丢弃这条样本。

「产品模式宽容、训练模式严格」：同一个修复动作，在产品里是兜底，在训练里是污染。 这条双重标准，体现的是 Harness 与模型训练的深度耦合。
