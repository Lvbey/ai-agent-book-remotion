5.1.1 — 5.1.6/阶段小结

六节讲完，其实是一条因果链

不是因为 Coding 重要才拿它当例子，是因为它同时具备三件事：能造工具、能被验证、有现成的工程基础设施。

ARC 01凭什么

代码是元能力

七个工具里没有「搜索网页」，但会写代码就有了一切：缺什么能力，当场造一个。 通用 Agent 也是把 Coding 当内核，把文件系统当中枢。

5.1.1 · 5.1.2

ARC 02怎么干

先认知，再动手，用测试收口

六个阶段里前三个一行代码都不写：补文档、澄清边界、写一页可被审的设计。 完成的标准不是「代码写完」，是「测试通过」。

5.1.3

ARC 03怎么稳

把判断权交给基础设施

四件组件、四层故障、三级恢复，每条路径都配上限。 这些东西一件都不在模型里——所以换模型，它们仍然成立。

5.1.4 · 5.1.5 · 5.1.6

串起来看：因为代码能造工具，它才接得住开放式任务；因为任务开放，才必须先对齐再动手； 因为动手的次数多了，稳定就只能靠工程，不能靠模型。
5.1.1 — 5.1.6/明天就能动

读完不用等新模型，下周就能动的三件事

三件事都不碰模型、不等版本，改的都是模型外面那一圈——而那一圈本来就是你团队现成的资产。

ACTION 01一小时

给仓库写一份指令文件

技术栈、目录职责、怎么跑测试、哪些目录别碰。 它每次会话自动注入，是最便宜的稳定前缀，也最不容易过期。

ACTION 02半天

把一条口头规范写成规则

「请遵循命名规范」是建议，「不符合就红」是约束。 先挑最常被违反的那一条，把它从文档搬进 Linter。

ACTION 03一天

给每条重试配一个上限

重试几次、退避多久、什么条件下放弃并交给人。 没有上限的重试，是账单上最贵的那类 bug。

判据只有一条：这套东西交给一个新来的远程同事，他能不能只靠仓库和文档独立干活。 能，Agent 也能；不能，先补仓库，别急着换模型。
