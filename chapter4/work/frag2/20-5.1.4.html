5.1.4 · Harness 工程/先把定义对齐

Harness 不是模型外面的一圈，它就是公式的另一半

第一章给过 Agent = Model + Harness。这里的 Harness 不止上下文和工具，还包含约束、验证、纠正——五样凑齐，才是一套完整的 Harness。

为什么先讲 Coding：代码任务的可验证性在所有 Agent 任务里最高，约束、验证、纠正三样都有现成基础设施可以依托—— 这是 Harness 红利最大的一个领域。
5.1.4 · 四件组件/缺一件就漏水

稳定不稳定，看的不是模型，是这四件东西

第一章的第二层，落到 Coding 场景就是四件可以逐条检查的工程组件——没有一件属于模型。

01验收基线

什么算做完了

测试套件、CI 管道、代码审查标准。把「做完了」从一个感觉，变成一次跑得出结果的检查。

02执行边界

能碰什么、不能碰什么

模块边界、依赖规则、权限控制。哪些目录、哪些接口不在可写范围里，写清楚。

03反馈信号

自动化的对错判断

Linter 输出、测试结果、类型检查错误。对错当场由机器判，不等人类说一句「不太对」。

04回退手段

出了问题怎么恢复

Git、沙盒隔离、快照回滚。做错了能一步退回去，它才敢试错。

分工：验收基线和执行边界负责「说清楚」——什么算对、什么不许碰； 反馈信号和回退手段负责「拉回来」——跑偏了当场发现，砸了能退回上一个好状态。
5.1.4 · 表 5-1/任务清晰度 × 验证自动化

Coding 天生站在最好的那个象限

两个维度切一刀：目标清不清晰、结果能不能自动验。四块地的瓶颈完全不同。

代码为什么天生在这个象限的核心：测试套件给验收标准，Linter 和类型检查给即时验证，Git 给回退—— 四件组件在这里全都有现货。
5.1.4 · 往哪推/四个瓶颈不一样

Harness 唯一的目标，是把任务往左上角推

四个格子的瓶颈不一样，所以「换一个更强的模型」只对其中一格有效。

一句话记住：加模型只解第一格；剩下三格要靠补验收标准、补人工吞吐、补目标定义——这些全是 Harness 的活。
5.1.4 · 成熟度的来源/不是代码模型特别强

Coding 成熟度最高，不是因为代码模型特别强

而是因为软件工程几十年攒下的基础设施，天然就是一套强大的 Harness——它们本来不是为 Agent 造的。

早就存在的设施 在 Harness 里担任 它本来是为谁造的
测试套件 · CI 验收基线 + 反馈信号 为「改代码别改坏」
Linter · 类型检查 反馈信号 为把规范写成可执行的规则
Git 分支 · 回滚 回退手段 为多人协作与合并
权限 · 模块边界 执行边界 为团队分工与隔离
可以迁移的判断：一个领域能被 Agent 自动化的程度，取决于它的「错」能不能被机器判定。 判得了，就能交给 Agent；判不了，模型再强也只能等人。
5.1.4 · 案例一/大规模代码迁移

大规模迁移赢在 Harness，不在模型

一家大型科技公司公开分享的迁移实践：任务量以万计，人不可能逐个看。真正的杠杆是三件 Harness 上的事。

01知识

知识必须活在代码库里

迁移规则、目标写法、历史先例都写进仓库里的文件。Agent 看不到的，等于不存在——开会讲一遍不算。

02约束

约束编进 Linter 和 CI

不写成文档等人自觉。规则一旦进了流水线，写法不对就提交不上去——不需要谁记得住。

03闭环

验证与纠正全链路自动

改完自动跑测试，报错自动回改，直到整条链路转绿。人只在最后抽样，不在中间守。

换个说法：知识若只存在于某个人嘴里，Agent 的规模上限就是那个人的时间。 把知识搬进仓库，才是「一万个文件」和「一百个文件」的区别。
5.1.4 · 案例二/LangChain

一行模型都没换，基准分数照样涨

只优化 Harness 的三个面——系统提示词、工具中间件、自验证循环——基准任务表现就显著提升。

01说清怎么干

系统提示词

任务边界、输出格式、什么时候该停下来问人。把默认做法写死，不让模型每次自由发挥。

02工具护栏

工具中间件

参数校验、失败重试、结果裁剪。脏数据在进上下文之前就被挡住，模型看不到，也就不会被它带偏。

03交卷前自查

自验证循环

交卷之前先跑一遍检查，不合格就自己重来。把「发现问题」提前到还没交出去的时候。

更值得抄的是方法论：用 Agent 去分析失败轨迹，再从轨迹里改 Harness。 这一步让 Harness 工程从「老师傅凭经验」，变成「看数据改配置」。
5.1.4 · 案例三/Anthropic 的长任务

长任务的两个老毛病，用两个角色治

一次想做太多、过早声称完成——这是长时运行 Agent 最常见的两种失败，也都不是模型能力问题。

TASKS.md · 跨轮次传递的中间成果
# 初始化 Agent 产出，执行 Agent 维护 [x] 01 抽出公共鉴权模块 [x] 02 迁移 user 服务 [ ] 03 迁移 order 服务 ← 下一轮从这里继续 [ ] 04 补集成测试 [ ] 05 删除旧鉴权代码 # 已完成的代码文件也在仓库里 services/order/ 已改 4 个文件
  • 初始化 Agent 只管拆。把大任务分解成一份可勾选的清单，先想清楚再动手。
  • 执行 Agent 只管推。一次只做清单上的一行，做完打勾，接着下一行。
  • 中间成果留在文件里。已改的代码、更新后的清单，下一轮直接接着用——不靠上下文记。
两个毛病各有一味药：拆清单治「一次想做太多」，清单上没打勾就不算完治「过早声称完成」。
5.1.4 · 收束/三个案例对位

三个案例，改的是同一个位置

都不是让模型更聪明，而是把「对不对」的判断权，从模型手里挪到基础设施手里。

案例 主要动了哪件组件 挪走了什么判断
大规模迁移 执行边界 + 反馈信号 规则从文档挪进 Linter 与 CI，写错就提交不上
LangChain 反馈信号 + 纠正 「哪里错了」改由失败轨迹来说，人只看轨迹
Anthropic 验收基线 + 纠正 「做完了」改由清单和文件说，模型无权宣布
一个可检验的推论：判断权一旦交出去，换不换模型就没那么要命了。 这也解释了为什么三个案例的收益，都不来自换一个更强的模型。
5.1.4 · 原则一/约束优先于指导

能强制的就别只建议，差别是「做不了」

能用代码强制的规则，就不要写成文档建议。前者是「做不了」，后者只是「建议别做」——中间隔着一整次模型自觉。

把一条口头规范改成一条检查
# 改造前：写在文档里，靠人看 PR 「禁止直接 import requests， 统一走 http/client.py」 # 改造后：写成一条会失败的检查 ci/lint.sh grep -rn "^import requests" src/ \ && exit 1 # PR 直接红，Agent 也读得到这行报错 # 附带效果：改完当场知道，不用等人说
  • 最小可执行的改造动作：翻出团队规范里最常被违反的一条，把它写成一条 lint 规则或一个 CI 检查。
  • 差别在长任务里会被放大。「做不了」一次生效；「建议别做」每一步都要重新赌一次模型的自觉。
  • 提示词该留给别的事：什么时候该停下来问人、输出成什么形状——这些本来就写不成检查。
判断标准很简单：这条规则，能不能写成一条会失败的检查？能，就别只写进文档。
5.1.4 · 原则二、三/验证与反馈

人工审查是瓶颈，而且反馈太慢

验证要自动化，因为人工审查不可扩展；反馈要快、要结构化，因为越接近出错时刻，纠正越省事。

维度 人工审查 自动化验证
吞吐 天花板是审查者的时间 与任务量无关，可以并行
延迟 几小时到几天 秒级，改完立刻出结果
判法 换个 reviewer 换一套标准 同一条规则，每次同一种判法
信息量 一句「这里不太对」 文件:行号 + 错误码 + 期望值
第二章的 Agent 状态栏就是这条原则的界面化：详细错误信息、工具调用计数器—— 把「哪里错了、错了几次」直接摆在模型面前，而不是让它自己猜。
5.1.4 · 原则四/回退与过程性错误

结果对不算完，过程错也是失败

回退要可靠——错误可逆，Agent 才敢大胆试错。而验收基线管结果，执行边界管过程：用错方法达成，同样是失败。

两条破坏性捷径 · 验收指标全绿
# 反例 1 · 修数据库连接故障 Agent → 把库删了，重新建 服务恢复 ✓　数据没了 ✗ # 反例 2 · 修编译错误 Agent → 删掉整个文件，重写 编译通过 ✓　实现没了 ✗ # 两单任务，验收指标都是绿的
  • 回退是试错的前提。Git 分支、沙盒环境、快照回滚——任何错误都可逆，它才敢动手。
  • 但指标挡不住捷径。把限制写进最终评估指标，Agent 也常能找到绕过去的办法，这就是 reward hacking 的日常形态。
  • 所以对动作设闸门。rm -rf、删生产数据、覆盖未读文件，执行前审批——约束的是动作，不只是结果。
一句话：结果指标是事后审计，动作审批是事前闸门。前者挡不住有意绕路，后者能—— 本章安全一节的语义解析、第四章的 Sidecar 复核，做的都是这道闸门。
5.1.4 · 工具编排/故障边界控制

一个工具挂了，不该带走整批任务

并行调用下，Harness 要回答一个模型不会回答的问题：一个失败，要不要连坐？

这就是反面教材的镜像：「一个命令失败，整个任务中止」是最脆的那种 Harness。 边界划对了，局部失败只是数据；划错了，一次网络抖动就能报废整轮工作。
