把闭环搬上屏幕

语音把时机轴压到毫秒，观察仍是一维的声音流；屏幕是二维的——
问题从「何时开口」变成「下一步点哪里」，以及点完之后现实是否还符合计划。

6.4 · 循环/看懂界面不等于完成任务

循环只有四步，难在第四步之后

截图、思考、执行、再截图——四步都能用现成组件拼出来，没有一处需要新发明。
难的是每一次点完，都要重新确认现实是否仍符合计划。

01

观察

截取当前屏幕，整屏像素就是这一轮的输入。

02

思考

多模态模型接住截图和任务指令，输出一段思考和一个具体动作。

03

执行

执行层落到真实环境：移动鼠标、点击、输入文字。

04

再观察

等界面响应后重新截图进入下一轮——这一步最容易被省掉，也最不能省。

看懂 ≠ 完成：「看懂界面」可以用一次截图问答测出来；
「完成任务」要求把理解和动作放进同一个闭环，处理页面加载、状态变化、误操作和不可逆后果。
6.4 · 设计维度/能做什么 · 点哪里 · 怎么想到

这个循环卡住的地方只有三处，每一处都能单独换

动作空间回答「它能做什么」，视觉定位回答「它点哪里」，模型架构回答「它怎么想到」。
前两个在 Harness 里改，换模型都不用动；第三个才是模型供应商的事。

01动作空间

它能做什么

鼠标、键盘、终端、文件编辑——决定这只手伸到像素、系统还是文件这一层。少了终端，它只能在一个界面里打转。

02视觉定位

它点在哪里

把「搜索框」这句话，落成一个可点击的编号或坐标。本节一半篇幅花在这里，因为绝大多数失败都发生在这一步。

03模型架构

它怎么想到

从截图直接生成动作，是训练出来的能力。工程只能约束输出格式，补不了那个「看一眼就知道点哪」的判断。

阅读顺序：6.4.1 动作 → 6.4.2 定位 → 6.4.3、6.4.4 回头改循环本身 → 6.4.5 换个战场。
6.4.1 · 动作空间/三类工具，一个循环

这三类工具是参考实现，不是必须遵守的协议

只要 Harness 能把同样的截图、动作约束和执行结果，翻译成目标模型支持的消息与结构化输出，
Claude、开放权重视觉模型、自托管端点都能驱动同一个循环。

6.4.2 · Grounding/选择题比填空题好答

把定位变成选择题，准确率先上一个台阶

开放式的那句「在截图中找到按钮并预测坐标」，被换成封闭式的一句「从已标注的元素里选一个」。
代价是：选项必须先被列出来，而且全都要塞进上下文。

路线怎么定位什么时候用代价
视觉标注 · SoM分割模型（SAM、SEEM）在像素上切出候选区域，叠编号，模型只报编号原生桌面软件、游戏、Canvas/WebGL——拿不到任何结构分割会漏检误检；标注图更费 token
结构化元素索引读 DOM 与 Accessibility Tree，枚举可交互元素并编号网页优先；桌面应用有无障碍树时同样适用标注信息全量进上下文，并不省 token
纯坐标预测模型直接看图报坐标，SeeClick 与 Claude computer use 走这条模型做过 GUI 定位训练，想省掉标注这一步依赖训练分辨率，换尺寸就系统性偏移
选择顺序：结构化信息可得时先用 DOM 索引；不可得时，通用模型走视觉标注，做过 GUI 定位训练的走坐标预测。 两者在小元素和密集界面上，精度都仍有差距。
6.4.2 · 结构化索引/标注来源从像素换成结构

DOM 拿得到时，别让它去猜坐标

SoM 用分割模型在像素上切区域；网页在渲染之前就已经有了元素树。
同一套「标注—编号—选一个」的思想，只是不用再猜。

取结构

通过 CDP 拿到网页的 DOM 树与无障碍信息。

02

筛可交互

自动挑出按钮、输入框、链接这些能点的元素。

03

编号画框

每个元素一个唯一 ID，并在截图上画出边界框。

04

生成清单

同时输出文本列表，说明每个 ID 对应哪个元素。

6.4.2 · 坐标预测/模型认的是分辨率，不是像素

坐标算错，多半是尺子不一样

模型对坐标的理解，绑死在训练时用的那几档分辨率上。
输入尺寸一变，它报的坐标就整体偏移——不是算错，是换算没做。

coordinate mapping · 双向缩放
# Claude 训练覆盖的三档 XGA 1024×768 · WXGA 1280×800 · FWXGA 1366×768 # 真实屏幕 2560×1440，宽高比 16:9 screen 2560×1440 → 挑 FWXGA 1366×768（同为 16:9） → 等比缩放后送入模型 model click (683, 384) x: 683 × 2560 / 1366 ≈ 1280 y: 384 × 1440 / 768 = 720 real click (1280, 720)
  • 按宽高比选档，不按面积。2560×1440 选 FWXGA，是因为三者里只有它同样是 16:9，不是因为它最大或最小。
  • 不能非等比拉伸。把 16:9 硬塞进 4:3 的 1024×768，画面被横向压扁，坐标判断跟着一起偏。
  • 双向缩放做在工具层。进模型前缩、出模型后反算，模型自始至终只看见 1366×768。
    • 6.4.3 · 观察接口/AOI：Agent–电脑观察接口

    屏幕不会静止，该改的是观察接口

    每 3–5 秒睁一次眼、而且没有耳朵的 Agent，对「两帧之间发生的事」既看不见也听不到。
    动作接口没有错——它还是点击和输入；错的是把连续观察压成了两张相隔很久的图。

    01关键帧

    只在有意义时截图

    用小模型判断屏幕是否发生了显著变化，变了才截。变化频繁时每秒 1 次，效果已经不错。

    02音量门控

    有声音才转写

    检测到声音才调语音识别，把识别出的文字放进上下文——Agent 从此有耳朵。

    03文字压缩

    截图换成一句话

    让模型把截图描述成一句话。原图后来被清出上下文，这句还在，多模态历史就这样压成了文本。

    换的是哪一层：核心思想是把连续的环境观察，切成模型便于处理的离散事件。 动作空间、坐标映射一个字没改，循环的输入端被重新设计了一遍。
    6.4.4 · 世界模型/先预测，再点击

    让它在点之前，先猜一遍后果

    观察接口解决的是「屏幕中间发生了什么」，它不解决串行循环本身的慢。
    人类点之前已经预判了后果；Agent 每点一次，都要重新看一遍。

    world model · 状态转移
    # 桌面状态 ≠ 一张像素图 state = 窗口 · 焦点 · 滚动位置 · 输入框内容 · 加载状态 · 权限 · 网络返回 act = click | type | scroll | drag | wait state + act ──> next_state (表示，不是截图) 一致 → 沿原计划继续（推测执行） 偏离 → 停下，重新观察和规划
  • 推测执行：预测与预期一致就继续走，只有偏离才停下来重看。省掉的是每一步的重新观察。
  • 要的是可检查的差异：「文件树多了一个文件、编辑器标题变了」，不是一张逼真的未来截图。
  • 先预演不可逆动作：删文件前在隔离的虚拟桌面里预测确认框，必要时先问人。
    • OSWorld-Human 的提醒：任务即使最终成功，Agent 的操作步骤仍明显多于人类、等待也更长。 准确率达到人类水平，不等于已经足够实用。
    6.4.5 · 移动端/技术能解，生态不解

    移动端难的不是手势，是有人不想让它点

    桌面上的对手是分辨率、加载和误操作；搬到手机上，对手换成了平台的收入结构。
    技术差异可以一个个填，商业冲突一个都填不了。

    01技术差异

    同一个 (x, y)，语义变了

    触摸没有「悬停」。它是单击、长按还是滑动的起点，得先用手势类型界定清楚，鼠标坐标那套语义在这里失效。

    02生态壁垒

    厂商试过，被封了

    手机厂商把 AI 助手接进消费级系统，让它代操作微信、淘宝、支付宝，很快遭遇平台限制。

    03技术差异

    读屏，而不是看图

    接 AccessibilityService 直接读界面元素、下发点击与输入，比截图识别稳。AndroidWorld 就在这个动作空间上评测。

    04生态壁垒

    变现链路被绕过

    AI 不看广告、不被推荐算法带走、也不冲动消费，直奔目标做完就走——每一次代操作都在侵蚀平台的收入根基。

    两种对抗：CAPTCHA 是技术层面的，靠更好的模型可以一点点磨过去； 商业模式是结构性冲突，短期难以调和——这才是消费级落地真正卡住的地方。
