5.1.1 · 基础能力/从一个最普通的任务说起

先看一个听起来不像编程的任务

「整理仓库中所有遗留的 TODO 注释，按优先级分类并生成 issue。」 —— 这更像「文档整理」，但它把 Coding Agent 需要的动作全走了一遍。

T01探索

浏览目录ls / glob

先搞清楚仓库长什么样：有哪些模块、哪些目录该跳过。

T02感知

读取代码read

打开具体文件，看清上下文再判断，而不是凭文件名猜。

T03定位

查找模式grep / search

在成千上万个文件里一次定位所有 TODO 出现的行。

T04执行

修改文件edit / write

把整理结果写成清单，或直接改代码加注释。

T05执行

运行命令bash

跑脚本统计、跑测试验证。

CONCLUSION一句话

这五类操作，覆盖了几乎所有 Coding Agent 的核心动作

所以工具集可以很小，小到只有七个——这正是下一节要展开的。

5.1.1 · 工具集/最小可用配置

七个工具，就是一个完整但极简的工具箱

在当前 SOTA 模型的加持下，具备基本 coding 能力并不需要复杂架构。这七件东西，几乎任何 Agent 系统都能低成本集成。

01沙盒

Code Interpreter代码解释器

在隔离沙盒里安全执行 Python。代码跑崩了也伤不到宿主机。

02执行

Bash Shell命令行终端

跑测试用例、处理特殊格式文件。一个几乎万能的执行入口。

03感知

Read读文件

读取代码、配置、文档、日志。Agent 的「眼睛」。

04执行

Write写文件

创建新文件，或把现有文件整体重写。

05核心动作

Edit编辑文件

只改局部。这是代码维护和迭代的核心操作。

06定位

Glob搜文件名

按模式匹配路径，如 **/*.py 捞出所有 Python 文件。

07定位

Grep搜文件内容

在内容里搜文本模式，比如「谁调用了这个函数」。

SUM成本

七件套 ≈ 一天工作量

没有隐藏依赖，没有专用平台，任何 Agent 系统都能接。

5.1.1 · 走一遍/七个工具只用了两个

两个工具，就完成了第一个任务

AGENT TRACE · TODO 清单整理
# 用户：帮我把项目里所有 TODO 注释整理成一个清单 Agent（思考）：需要找到所有包含 TODO 的代码行。 Agent → Grep(「TODO」, glob=「**/*.py」) # 搜索内容 工具返回： src/api.py:42: # TODO: add rate limiting src/db.py:15: # TODO: migrate to PostgreSQL tests/test_api.py:8: # TODO: add edge case tests Agent（思考）：找到 3 个，整理成清单写入文件。 Agent → Write(「TODO_LIST.md」, content=「...」) # 写文件 工具返回：文件已创建 Agent：已整理完毕，共 3 项，清单保存在 TODO_LIST.md。
  • 两步就收工。只用了 7 个工具里的 2 个——Grep 定位，Write 落盘。没有规划器、没有多 Agent 编排。
  • 任务一变，工具跟着变。如果换成「统计每个模块的 TODO 数量并画柱状图」，Agent 会再加上 Code Interpreter 执行 Python 做统计和绘图。
  • 组合爆炸才是关键。七个原子动作，组合出来的任务空间几乎是无限的——这就是「极简工具箱」能撑起通用 Agent 的原因。
对传统开发者的类比：这就是一套最小 CLI。
glob → ls -R ｜ grep → grep -rn ｜ read → cat ｜ edit → patch
5.1.1 · 设计取舍/工具数量不是重点

一个 Bash 就能干完大半，为什么还要七个？

这个问题原文自己回答了，而且答案比「多几个工具」更有意思——它暴露了不同厂商对 「编辑」这件事该不该被显式建模的分歧。

路线 AOpenAI Codex

极简：shell 唯一入口 + apply_patch

用 shell 完成目录浏览、文件查找与读取；文件修改则交给一个语法受约束的 apply_patch 工具—— 把编辑表达为结构化补丁，而不是自由文本命令。

好处：降低「改错文件」的概率。补丁要么对得上，要么直接失败。

路线 B本书 / 多数 Agent

显式：读写编辑各占一个工具

保留单独的 Read / Write / Edit，工具边界清晰，模型一眼能看出「我现在是要读、要覆盖、还是只改一段」。

本书选七个，是为了让读者看清 Coding Agent 到底需要哪些基本能力。

结论：七个不是标准答案，是一个「可读性优先」的教学切分。 真正的设计问题是——哪几个原子动作必须被显式建模，才能让模型不犯错。 一旦你的沙盒里能跑 bash，六个、七个、三个都能工作，区别只在出错时的可恢复性。
5.1.1 · 与第四章对齐/别把两套分类搞混

七个工具，只覆盖了五类通用工具里的两类

第四章按调用方向和作用性质把工具分成五类；这里的七个是 Coding Agent 的 特有基础配置。两套分类维度不同，不要混着记。

第四章的五类七个工具中的对应说明
感知 Read · Glob · Grep 看文件、看路径、看内容。Agent 获取信息的全部入口。
执行 Bash · Code Interpreter · Write · Edit 跑命令、跑代码、改文件。Agent 改变世界的全部出口。
协作 — 多 Agent 之间的任务分派与结果汇总，本章不涉及（见第 10 章）。
事件触发 — 定时器、Webhook、异步回调（见第 6 章）。
用户沟通 — 提问、确认、展示产物。Coding Agent 通常直接对话，不需要专门工具。
一句话记住：七件套 = 感知 + 执行。它解决的是「Agent 能不能动手」， 不解决「Agent 怎么跟别人协作、怎么被叫醒、怎么跟人确认」——那三类是叠加在之上的。
5.1.1 · 为什么值得做/四个真实场景

代码不是「写程序」，是通用的问题解决手段

为什么每个通用 Agent 都该有 coding 能力？因为这四种情况，你迟早会撞上—— 而它们都不在「编程」的语境里。

01思考

数学推理算得准，不是算得像

写段代码交给求解器，拿精确答案，而不是靠模型「心算」。模型的思考是概率性的，数学要的是确定性的。

02约束

固化业务规则7 天到底是几天

「购买后 7 天内可退款」——自然日还是工作日？下单时间还是发货时间？代码没有歧义。

03扩展

临时造工具缺什么就写一个

工具箱不必预先穷举。遇到没见过的需求，当场生成一个小脚本补上缺口。

04适应

格式变了动态生成解析逻辑

上游接口字段漂移，等人改代码要排期；让 Agent 看着样本现场写解析，几分钟适配。

这就是「元能力」的雏形：工具箱里只有七个简单工具，但能力边界可以随时扩张—— 因为它能当场造出第八个、第九个工具。下一节 5.2 会把这六个方向完整展开。

SECTION 05.1.2

从 Manus 到 OpenClaw
通用 Agent 的 Coding 内核

这类产品把三种能力装进同一个系统：
Deep Research（深度调研）、Computer Use（电脑操控）、Coding（代码生成）。

CAP 01输入

Deep Research

搜、读、核对、综合成结论。

CAP 02手脚

Computer Use

看屏幕、点鼠标、敲键盘。

CAP 03内核

Code Generation

写代码、跑代码、改代码。

问题来了：为什么核心是 Coding，而不是另外两个？

5.1.2 · 架构判断/几乎一切产出最终都落到代码

三种能力，一个内核

因为几乎所有高效的内容生成，最终都要落到代码上。 代码生成是效率最高、成本最低、可复用性最强的能力基座——另外两个能力，很多时候只是代码能力的「降级替代」。

WHY CODE IS THE CORE
// 三大能力各自的最优实现路径 Deep Research → 代码驱动的 Web 请求与解析 ✓ 最优 → 浏览器视觉操作 ✗ 慢 Computer Use → 调用 API / 写脚本 ✓ 最优 → 点鼠标、找坐标 ✗ 脆 Coding → 写代码 ✓ 唯一 // 结论：另外两个能力，最终都在调用它
  • 成本：一次 API 调用是几分钱，一次 GUI 操作是几十秒的视觉推理。差两个数量级。
  • 延迟：代码执行毫秒级；Computer Use 要截图、要定位、要规划下一步。
  • 稳定性：接口签名稳定；界面改一版像素，鼠标坐标就全废。
  • 可复用：写下的脚本能存下来、能版本控制、能给别人用；一次成功的点击序列不能。
所以 Computer Use 不是不重要，而是「没有别的路时才走的路」—— 凡是能用代码或 API 完成的，都该用代码。用代码省下来的钱和时间，才是通用 Agent 能规模化服务的前提。
5.1.2 · 证据/你以为在生成内容，其实在生成代码

五种产物，底层全是代码

你以为 Agent 在生成它真正的代码形态为什么这件事重要
PPT / Word 文档 OOXML（Office Open XML） 本质是 zip 包里的一堆 XML。所以「改一页版式」= 改一段结构化代码，不需要视觉定位。
PDF 报告 Markdown / HTML / LaTeX 先写源码再编译。Agent 能精确控制分页、图表位置、字体层级。
数据分析与图表 Python 脚本 pandas 聚合 + matplotlib 绘图。数字由代码算，不经过模型「抄写」，所以不会抄错。
浏览器里的操作序列 可复用的 RPA 代码 一次成功的点击序列可以固化成脚本，下次直接跑，不必再付视觉推理的成本。
深度调研结论 Web 请求 + 解析代码 抓取、清洗、比对都由代码完成；模型只负责判断「哪些值得读」。
一句话：内容生成的天花板，不是模型的文笔，而是它能不能把意图翻译成一份可执行的、可验证的代码。 翻译得了，就能自动化；翻译不了，就只能靠人。

5.1.2 · 一次真实执行/五步全部落在文件上

「分析上季度销售数据，生成一份总结报告」

01

读记忆

读 MEMORY.md：用户偏好 PDF 格式的报告，数据源是 Google Sheets。不用再问一遍。

02

调工具

通过网络搜索模块拿到 Sheets API 用法，再用代码执行把数据下载到本地。

03

写代码

生成 Python 脚本：pandas 做聚合，matplotlib 出图。数字由代码算，不由模型算。

04

生成产物

分析结果写入 report.pdf，图表写入 charts/ 目录。

05

更新记忆

在 MEMORY.md 记下 「User's sales data is in Google Sheets, ID: xxx」，下次直接开始干活。

WORKSPACE AFTER TASK
~/ ├─ MEMORY.md # 用户偏好 + 数据源 ID │ └ 本次新增 1 行 ├─ memory/ │ └─ 2026-11-04.md # 今天的日志 ├─ charts/ │ ├─ revenue.png │ └─ region.png ├─ report.pdf # 最终交付物 └─ scripts/ └─ analyze.py # 可复用
注意第 5 步。这一步没有产出任何「用户可见」的东西，但它让下一次执行成本下降—— 记忆是复利，而它保存在一个 Markdown 文件里。
5.1.2 · 记忆层/为什么是 Markdown 而不是向量库

文件系统不只是存储，是记忆、知识和能力的中枢

MEMORY.md · 长这样
# 用户偏好 - 报告格式：PDF - 语言：中文 - 称呼：Bojie # 环境事实 - 数据源：Google Sheets ID: 1a2b3c... - 时区：Asia/Shanghai # 经验 - 该银行电话验证需要开户行地址 （2026-10-22 实测）

选择 Markdown 而不是向量数据库，看起来反直觉，实际上极其有效：

  • 用户能直接读、直接改。Agent 记错了某件事？打开文件删掉那一行就行——不需要「重训」，也不需要写一条纠正指令。
  • 天然保留时间顺序。按日期归档的日志，避免了语义检索里最常见的时间混淆（「上周说的」和「上个月说的」混在一起）。
  • 可以进 Git。版本控制、diff、回滚——记忆的每一次变化都可追溯。
更关键的一点：Agent 有写文件的能力，就意味着它具备了修改自身外部产物的技术条件。 第一次做某个任务时发现的新知识（比如「这家银行要开户行地址才能验证身份」），可以先写进记录—— 什么时候这条记录足够可靠、能升级成知识或程序，是第 9 章要讨论的持续进化问题。
5.1.2 · 别推过头/这个判断有边界

「Coding 是核心」只对开放任务型 Agent 成立

原文在这里做了一个重要的自我限定。如果你把它理解成「所有 Agent 都该以 Coding 为中心」，就会做错架构决策。

维度开放任务型通用 Agent垂直领域 Agent（如客服）
任务边界 不确定。任务千变万化，无法预先枚举所需工具 相对封闭。围绕固定业务流程、领域工具、对话策略构建
产物形态 多样：报告 / 表格 / 网页 / 视频 / 代码 稳定：回答、工单、退款单、订单变更
代码的角色 架构中枢——元能力，动态扩展能力边界最经济的路径 工具箱里的一件工具，不是架构中枢
代表 Manus、OpenClaw、Claude Cowork τ-bench 里的航空 / 电商客服 Agent
但注意后半句：即便在垂直 Agent 里，coding 仍是重要的基础能力—— 精确计算、数据处理、规则校验都离不开它。区别只是：它是「必备零件」，而不是「承重墙」。

5.1.3 · 项目文档化/知识必须存在于代码库里

README 给人读，指令文件给 Agent 读

仓库里的知识有两种读者：写给人的那份讲究叙事，写给 Agent 的那份讲究约束。

文件写给谁承载什么
README.md 新加入的开发者 这是什么项目、怎么装、怎么跑起来。第一次接触时读。
CLAUDE.md · AGENTS.md 本项目的 Agent 行为约定：构建与测试命令、代码风格、明确禁区。每次会话自动注入。
SOUL.md OpenClaw 的 Agent 身份与行为规则——约定「Agent 是谁」，跨项目不变。
MEMORY.md 同一个 Agent 跨会话沉淀的经验与用户偏好——约定「这个用户怎么伺候」。
  • 自动注入 = 项目级系统提示词。每个会话开始时它已经在上下文里，不用你在对话里重复交代项目规矩。.cursorrules 也是同一类东西，只是名字不同。
  • 它还是最经济的稳定前缀。内容不随任务变化，天然对 KV Cache 友好——省的是钱，也是首字延迟。
作者给出的 AI-ready 判据：一个远程新人，只靠代码仓库和文档，能不能独立开展工作。能，说明知识真的写在了代码库里，Agent 也读得到。
5.1.3 · 需求与设计/把模糊需求压成一页可审查的计划

设计文档不是交付物，是换取一次人类审查的接口

复杂性有三个来源：需求本身模糊、实现路径多样、影响范围广。
任何一个，都足以让「直接开干」变成返工。

DESIGN DOC · 四个必答问题
# 一页纸，回答四件事 ① 修改哪些模块，为什么是它们 ② 采用什么方案，优势在哪 ③ 引入哪些新依赖 ④ 预期对系统的影响 # 写的过程 = 编码前的预演 # 提交人审 → 批准 → 才动手

「优化系统性能」这五个字，至少藏着三个必须先问清的问题：

  • 目标是什么？降响应时间、省内存，还是提吞吐量——三者常常互相拉扯，得先定一个主指标。
  • 可接受什么权衡？能不能改接口、能不能牺牲一部分易用性，必须先谈清楚。
  • 瓶颈在哪？慢在查询、渲染还是网络，有没有数据支撑，还是凭感觉猜。
  • 为什么值这一页纸？审查一页设计文档，比审查几百行代码便宜得多。
写文档不是走流程：它逼 Agent 在概念层先把方案跑一遍。很多方案在读代码、画调用链的时候就被自己否掉了——那时还没花一行代码的成本。
5.1.3 · 实现与验收/由验证判定何时可以停

完成的标准是测试通过，不是代码写完

设计获批之后才动键盘。实现不是终点——写代码、跑测试、自我审查，是同一段循环里的三个动作。

01

按规范实现

遵循项目代码规范，复用已有抽象和工具；不为这次任务另造一套写法，必要时做适度重构。

02

写测试

覆盖正常路径、边界条件、异常情况，而不是只测一遍「能跑通的那条路」。

03

跑测试，进入「测试-修复」循环

不是把失败原样上报：读报错、定位、改代码、重跑。可能迭代多轮，直到全部通过。

04

自我审查

可读性、注释是否足够、有无性能与安全隐患、是否符合风格——读代码、跑 lint，或调用专门的审查子 Agent。

最常见的偷懒：写完代码不跑测试，直接报告「任务完成」。把「测试通过」而不是「代码写完」定义为完成标准， 正是 Loop 工程「由验证判定何时可以停」在编码场景的落地。
5.1.3 · 现实中的裁剪/推荐流程不是必选流程

同一套流程，不同模型裁剪的位置不一样

SIMPLE跳过设计文档

简单 bug 修复

改一个已知缺陷、调一个参数：直接进入实现，但测试这一步仍然要跑。

COMPLEX走完整流程

复杂且影响面大

跨模块、路径不确定：六个阶段一个不落，设计文档必须先过人类审查。

动手之前先调查型先提交型
读多少 目录、实现、调用方、测试，读到能画出调用链 只读几个最可能相关的文件
怎么改 想清楚再动手，第一次提交就接近正确 先提交补丁，把编译与测试的报错当作调查

这个「何时停止收集信息、开始行动」的阈值，换 Harness 可能不变，换模型却可能变——
它首先是模型学到的行为策略，不是 Coding 产品的界面风格。

Harness 的提示词、工具和预算能放大或抑制它，但不必是它的来源。第七章在固定 Harness 里衡量这一差异，第八章再从后训练角度解释它怎样写进参数。
5.1.4 · Harness 工程/四件组件，缺一件就漏水

稳定运行不取决于模型，取决于这四件东西

让 Agent 能做事的那一半，前面几节已经搭完了。
这一节讲的全是另一半——让它不做错事，而这四件组件没有一件属于模型。

01验收基线

什么算做完了

测试套件、CI 管道、代码审查标准。把「做完了」从一个感觉，变成一个能跑出结果的检查。

02执行边界

能碰什么、不能碰什么

模块边界、依赖规则、权限控制。明确写下哪些目录、哪些接口不在可写范围里，碰了要报错。

03反馈信号

自动化的对错判断

Linter 输出、测试结果、类型检查错误。对错由机器当场判，不等人类回一句「不太对」。

04回退手段

出了问题怎么恢复

Git 分支、沙盒隔离、快照回滚。做错了能一步退回去，它才敢试错。

四件组件的分工：验收基线和执行边界负责「说清楚」——什么算对、什么不许碰； 反馈信号和回退手段负责「拉回来」——跑偏了当场发现，砸了能退到上一个好状态。

5.1.4 · 业界实践/三个案例，一个位置

三家改的都不是模型，是模型外面的那圈东西

大规模迁移看「知识放在哪」，LangChain 看「谁来改 Harness」，
Anthropic 看「长任务怎么拆」——三处改动都在模型外面。

CASE 01大规模代码迁移

让知识活在代码库里

知识必须活在代码库里——看不到等于不存在。
约束编码进 Linter 与 CI，不写进文档。
验证与纠正，全链路自动化。

CASE 02LangChain

只动外壳，分数就上去

只优化提示词、工具中间件与自验证循环，
基准表现就显著提升。更狠的一步：
用 Agent 分析失败轨迹，反过来改 Harness。

CASE 03Anthropic

把长任务劈成两个角色

初始化 Agent 只管拆清单，执行 Agent 逐步推进，
中间成果留给下一轮继续用。
治的是「一次想做太多」和「过早声称完成」。

三个案例，同一个动作：把「对不对」的判断权，从模型手里挪到基础设施手里。 连「怎么改 Harness」这件事，也交给了 Agent 去分析——从人工经验，转向数据驱动。
5.1.4 · 可迁移原则/换一个场景也成立

能强制的就别只建议，这四条不止对 Coding 成立

原文把它们称为「从 Coding Agent 到通用 Harness 的设计原则」。四条的共同点： 都不要求模型更聪明。

原则 落到什么工程上 为什么成立
约束优先于指导 Linter 规则、类型约束、CI 检查 前者是「做不了」，后者只是「建议别做」
验证要自动化 测试套件、代码质量检查、行为监控 人工审查是不可扩展的瓶颈
反馈越快越结构化 详细错误信息、工具调用计数器 越接近出错时刻，纠正效率越高
回退要可靠 Git 分支、沙盒环境、快照机制 错误可逆，才敢大胆试错
这四条不是并列的：先是能不能做错（约束），再是怎么知道错了（验证与反馈），最后是错了怎么办（回退）。 换个场景也照抄：写文档不如写检查，加人手不如加流水线。
5.1.4 · 约束的第二层/结果对，过程也可能错

结果对不算完，用错方法达成也是失败

验收基线管结果，执行边界管过程。下面这两个「修复」，验收指标全绿。

两条破坏性捷径 · 指标都过了
# 反例 1 · 修数据库连接故障 Agent → 把库删了，重建 服务恢复 ✓　数据没了 ✗ # 反例 2 · 修编译错误 Agent → 删掉整个文件，重写 编译通过 ✓　实现没了 ✗ # 两个任务，验收指标都是绿的
  • 所以要对动作设检查。rm -rf、删生产数据、覆盖未读文件——这类操作要在执行前审批，约束的是动作，不只是结果。
  • 指标挡不住，就在路径上挡。本章安全一节的语义解析、第四章的 Sidecar 复核，做的都是这道检查。
  • 工具编排也要划故障边界。并行调用里一个失败，只中止同一批里依赖它的调用——同时读三个文件，一个找不到就只报这一个。
这就是 reward hacking 的日常形态：把限制写进最终评估指标，Agent 也常能找到绕过去的办法。 第八章的 RLVP 因此「奖励结果、惩罚路径」。
5.1.5 · 故障分类/按发生的位置切成四层

先按位置分类，再谈恢复

5.1.4 的四个组件里，最能拉开工程差距的就是故障恢复。而恢复的第一步不是重试， 是先知道自己撞上的是哪一层故障——层不同，处置手段完全不同。

L1基础设施

API 层API LAYER

限流 429、服务过载、请求超时、连接中断、输出触顶被截断——与任务内容无关，是基础设施的噪声。

L2手脚

工具层TOOL LAYER

幻觉调用、参数畸形、执行抛异常；最危险的是同一个错误反复返回，而模型原样重试。

L3记忆

上下文层CONTEXT LAYER

窗口溢出、压缩失败、轨迹结构损坏——比如工具调用缺少配对的结果消息。

L4循环

控制流层CONTROL LAYER

死循环：反复做同一件事却毫无进展。死亡螺旋（death spiral）：恢复逻辑自己又调 LLM，再出错，连锁。

第一章的消融实验已经演示过：仅仅缺失一条工具结果反馈，就足以让 Agent 陷入无限循环。 真实生产的故障远比实验里多样——所以先分层，别把所有异常都当成「重试一下就好」。
5.1.5 · 检测/先分类，再计数

先判断值不值得，再决定怎么重试

判断的不是「要不要重试」，而是「值不值得」。Harness 因此维护一张「错误 → 恢复策略」映射表。

捕获到的故障可重试？该做什么
限流 429 · 服务过载 · 网络抖动 可重试 同一个请求，退避之后再发。
参数不合法 · 参数畸形 不可重试 原样重发多少次都是同样结果，必须改输入。
权限不足 · 工具不存在 不可重试 改变策略：升级人工，或把错误喂回给模型。
输出触顶被截断 可重试 但请求本身要变——提高上限，或从断点接续。
  • 重复调用指纹：对「工具名 + 参数」算指纹，同一指纹反复出现，就是无进展循环的明确信号。
  • 连续失败计数：每条恢复路径独立计数，是熔断（circuit breaker，连续失败到阈值就掐断这条路径）的依据。
  • 活性监控：最危险的失败不是断开，而是静默卡死——连接在、数据不来。SDK 超时只管建连，需独立的空闲看门狗（watchdog timer，超时无新输出即判定卡死）。
  • 完整性监控：轨迹缺配对结果时，在注入上下文前自动修复，而不是把结构异常抛给模型。
「产品模式宽容、训练模式严格」：产品侧用占位符补齐，训练侧拒绝修复——合成占位符会污染训练数据。
5.1.5 · 恢复/按对用户透明的程度分级

能用低一级的手段，就不要升级

三级手段，逐级透明。前两级对用户完全不可见——中间态在恢复期间被扣住，成功则毫无感知。

01

静默重试

指数退避叠加随机抖动，避免大量客户端同步重试造成二次拥塞，并尊重服务端返回的等待提示。还要区分前台与后台：主循环失败要重试，标题生成、输入建议这类后台调用失败直接放弃，否则会挤占主链路配额，形成重试放大。

02

降级与接续

改变请求本身再试。输出触顶：先提升上限重发，仍不够就追加元指令从断点接续。主模型持续过载：降到备用模型，但需先剥离旧模型的私有格式块。高成本模式被限流：暂时回落标准模式。

03

暴露给用户

所有自动手段用尽后才呈现错误，并附上已经尝试过的恢复动作——用户接手时知道自己处在哪一步。

TOOL ERROR · 走另一条路
# 工具层错误不终止会话 不做 终止会话、把异常抛给用户 只做 把错误装成一条工具结果 幻觉调用 → 「工具不存在」的结构化结果 参数校验失败 → 附带输入约束提示的错误 畸形参数 → 执行前先经程序化修复 # 下一轮由模型自行纠正（错误越具体，成功率越高）
本节的核心原则：错误处理的边界不是单次请求，而是整个恢复循环。确认无法恢复之前， 中间错误不暴露给消费者——无论是用户，还是订阅事件的下游系统。
5.1.5 · 接管/把没跑完的轨迹交给另一家

能带走的是文字，带不走的是凭证

主模型持续不可用时，要换一家把这条轨迹接着跑完。障碍不在接口地址，在轨迹里那些只属于原厂商的东西。

TRAJECTORY · 中立格式
# 每段思考拆成两半 [01] thought text : 「先读 package.json」 token : 厂商凭证 ✗ 丢弃 [02] tool_call read_file args : {"path":"package.json"} [03] tool_result ref : call #02 # 标识符 → 渲染目标请求时才重新生成 # 切换时丢弃凭证，文字当普通内容带入
  • 工具调用好办：各家结构不同，但语义一致，按目标厂商重新渲染即可。
  • 难办的是思考：可读文字之上还附了凭证，用来证明「这段思考确实出自它自己」。文字换一家照样读得懂，凭证换一家就失效。
  • 凭证的位置还不统一：有的根本不校验，有的拒绝一切非自己签发的，有的把它附在工具调用上。所以「把思考删干净就安全」在某些厂商那里反而通不过。
  • 所以方案按最严格的一端设计，并留退路：把历史工具调用改写成文字叙述——模型不再当它是真调用过，但至少能接着往下跑。
  • 厂商已经备好一份副本：思考摘要本就是为跨厂商场合准备的可移植副本，保留即可，不必再调一次模型重新压缩。
设计原则：轨迹不该按任何一家的接口格式存储，而应保存为中立格式——第七章的评估重放、第八章的训练样本、第九章的经验提取，依赖的都是同一份产物。
5.1.5 · 终止/每条恢复路径都要有上限

恢复机制本身会失效，所以它也需要熔断

单点熔断管住一条路径，死亡螺旋管住路径之间的连锁——两者都靠「提前定好上限」。

01单条路径封顶

单点熔断CIRCUIT BREAKER

上下文压缩连续失败若干次就放弃压缩；权限分类失败就回退人工询问；输出接续最多固定轮数。每条路径独立计数、独立封顶，一条走到头不影响另一条。

02路径之间的连锁

死亡螺旋防护DEATH SPIRAL

在错误路径上禁用一切会再次调用模型的副作用逻辑；再用递归深度计数器打断残余连锁。真实案例：溢出停止 → 触发「自动提交代码」停止钩子（结束时自动执行的清理逻辑）→ 钩子调 LLM 写 commit message → 又溢出 → 又触发钩子。

THRESHOLD阈值从生产数据来，不靠拍脑袋

连续 3 次CLAUDE CODE · 上下文压缩熔断

曾有一个会话在这条恢复路径上连续失败三千余次；这类无效重试每天在全球造成约 25 万次 API 调用浪费，逾千个会话出现过 50 次以上连续失败。3 次，正是「绝大多数故障在此之前已恢复」与「继续重试基本无望」之间的经验拐点。

最后还有一层全局兜底：在所有自动化机制之上，仍需最大迭代轮数、会话预算上限， 以及连续失败超阈值时升级到人工干预——自动化管路径，全局条件管整个会话。
5.1.6 · 执行机制/不等整轮生成完

第一个调用的参数一完整，就开始跑

5.1.4 只定了原则——一个失败不该拖垮整批。这一页讲机制：等待怎么重叠，中止怎么划边界。

01等待

串行在排队

生成 → 执行 → 拿结果 → 再决定下一步，每一步都在等上一步跑完。

02重叠

流式让等待重叠

第一个参数一完整、通过校验就开跑，与后两个调用的生成过程同时进行。

03边界

失败要级联中止

每个工具声明是否支持并发（默认否）；只中止同批依赖失败结果的调用，不波及独立调用与父级。

5.1.6 · 上下文管理/按行号读，不读全文

代码库比上下文大得多，所以读也要分页

百万级窗口听起来够用，把整个仓库塞进去却既不经济也没必要。上下文管理的第一步，是让「读」本身带上粒度。

READ · 按行号范围取，返回带行号
Agent → read("src/main.py", 100..150) 工具返回： 100| def handle_request(req): 101| token = req.headers["auth"] 102| user = verify(token, cfg) …（中间 39 行省略） 142| return jsonify(resp) # 3,842 行的文件，只进来 51 行 Agent → edit("src/main.py:142", …)
  • 不要总读全文。大型文件按行号范围取片段——几千行的仓库文件，一次只加载真正要看的那一段。
  • 行号前缀换精度。每行以实际行号打头，模型才能说「第 142 行」；引用没有歧义，后续编辑才落得准。
  • 终端输出要掐头去尾。保留前若干行（错误上下文）与后若干行（错误总结），中间一行提示替代，并说明完整输出已存到临时文件。
不是新机制：这几条都是第四章「长输出截断 + 持久化」在编程场景的落地——上下文里只留判断所需的部分，其余留在文件里按需取。
5.1.6 · 环境感知/状态栏的编程版

模型缺的不是更长的提示词，是当前状态的快照

第二章讲过的 Agent 状态栏，在 Coding Agent 里不是装饰——它决定每个决策基于现状，还是基于一个过时的假设。

启动时创建一个终端并全程保持。否则 cd 过的目录、激活的虚拟环境、设的环境变量、起的后台服务，下一条命令全部丢失。仍应保留隔离终端以支持并行任务，但持久化是默认。

05错误即现

即时语法反馈

文件写入一完成就自动跑 linter 或语法检查，结果作为工具返回值的一部分回到模型——下一轮推理立刻看到，像 IDE 里打错一个括号就画红线。

SUM五个技巧，一个目标

并行与流式 · 上下文管理 · 环境感知 · 状态持久化 · 即时反馈

它们不是五个孤立的优化点，而是相互配合的设计决策——指向同一件事：让 Agent 像经验丰富的开发者那样流畅地工作。

为什么即时反馈值钱：错误在引入的那一刻就被修正，而不是等到跑测试才发现——这正是它「显著降低修复成本」的原因。
5.1.1 — 5.1.6/阶段小结

这六节讲完，只剩三句话

ANCHOR 01能力

工具箱极小，能力边界极大

五个动作、七个工具就能支撑开放任务；而代码是元能力——缺什么能力，当场造一个。 产物与记忆都落在文件系统里，可读、可改、可回滚。

ANCHOR 02流程

先理解，再动手，用测试收口

六个阶段里前三个一行代码都不写：补文档、澄清边界、写一页可被审的设计。 完成的标准不是「代码写完」，是「测试通过」——这条线守住了，它才从生成器变成工程助手。

ANCHOR 03基建

稳定不靠模型，靠模型外面那圈

验收基线、执行边界、反馈信号、回退手段——四件组件没有一件属于模型。 故障按层分类、按值得与否决定重试、按透明度分级恢复，每条路径都要有熔断上限。

它跑得稳，不是因为模型更强，
而是因为模型外面那圈东西更硬。

TAKEAWAY 01

把四个问题写进工程里：什么算做完、能碰什么、错在哪、怎么退回去。这四件事没有一件属于模型。

TAKEAWAY 02

你团队那套测试、类型、Lint、版本控制，换个使用者（Agent）就能直接复用——这是传统开发者现成的起跑优势。

TAKEAWAY 03

自动化能走到哪一步，取决于验证能不能自动化。凡是「对不对」还得靠人点头的环节，就是吞吐量的天花板。
