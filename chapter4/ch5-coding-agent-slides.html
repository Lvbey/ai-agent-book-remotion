5.1.1 · 基础能力/从一个最普通的任务说起

先看一个听起来不像编程的任务

「整理仓库中所有遗留的 TODO 注释，按优先级分类并生成 issue。」 —— 这更像「文档整理」，但它把 Coding Agent 需要的动作全走了一遍。

T01探索

浏览目录ls / glob

先搞清楚仓库长什么样：有哪些模块、哪些目录该跳过。

T02感知

读取代码read

打开具体文件，看清上下文再判断，而不是凭文件名猜。

T03定位

查找模式grep / search

在成千上万个文件里一次定位所有 TODO 出现的行。

T04执行

修改文件edit / write

把整理结果写成清单，或直接改代码加注释。

T05执行

运行命令bash

跑脚本统计、跑测试验证。

CONCLUSION一句话

这五类操作，覆盖了几乎所有 Coding Agent 的核心动作

所以工具集可以很小，小到只有七个——这正是下一节要展开的。

5.1.1 · 工具集/最小可用配置

七个工具，就是一个完整但极简的工具箱

在当前 SOTA 模型的加持下，具备基本 coding 能力并不需要复杂架构。这七件东西，几乎任何 Agent 系统都能低成本集成。

01沙盒

Code Interpreter代码解释器

在隔离沙盒里安全执行 Python。代码跑崩了也伤不到宿主机。

02执行

Bash Shell命令行终端

跑测试用例、处理特殊格式文件。一个几乎万能的执行入口。

03感知

Read读文件

读取代码、配置、文档、日志。Agent 的「眼睛」。

04执行

Write写文件

创建新文件，或把现有文件整体重写。

05核心动作

Edit编辑文件

只改局部。这是代码维护和迭代的核心操作。

06定位

Glob搜文件名

按模式匹配路径，如 **/*.py 捞出所有 Python 文件。

07定位

Grep搜文件内容

在内容里搜文本模式，比如「谁调用了这个函数」。

SUM成本

七件套 ≈ 一天工作量

没有隐藏依赖，没有专用平台，任何 Agent 系统都能接。

5.1.1 · 走一遍/七个工具只用了两个

两个工具，就完成了第一个任务

AGENT TRACE · TODO 清单整理
# 用户：帮我把项目里所有 TODO 注释整理成一个清单 Agent（思考）：需要找到所有包含 TODO 的代码行。 Agent → Grep(「TODO」, glob=「**/*.py」) # 搜索内容 工具返回： src/api.py:42: # TODO: add rate limiting src/db.py:15: # TODO: migrate to PostgreSQL tests/test_api.py:8: # TODO: add edge case tests Agent（思考）：找到 3 个，整理成清单写入文件。 Agent → Write(「TODO_LIST.md」, content=「...」) # 写文件 工具返回：文件已创建 Agent：已整理完毕，共 3 项，清单保存在 TODO_LIST.md。
  • 两步就收工。只用了 7 个工具里的 2 个——Grep 定位，Write 落盘。没有规划器、没有多 Agent 编排。
  • 任务一变，工具跟着变。如果换成「统计每个模块的 TODO 数量并画柱状图」，Agent 会再加上 Code Interpreter 执行 Python 做统计和绘图。
  • 组合爆炸才是关键。七个原子动作，组合出来的任务空间几乎是无限的——这就是「极简工具箱」能撑起通用 Agent 的原因。
对传统开发者的类比：这就是一套最小 CLI。
glob → ls -R ｜ grep → grep -rn ｜ read → cat ｜ edit → patch
5.1.1 · 设计取舍/工具数量不是重点

一个 Bash 就能干完大半，为什么还要七个？

这个问题原文自己回答了，而且答案比「多几个工具」更有意思——它暴露了不同厂商对 「编辑」这件事该不该被显式建模的分歧。

路线 AOpenAI Codex

极简：shell 唯一入口 + apply_patch

用 shell 完成目录浏览、文件查找与读取；文件修改则交给一个语法受约束的 apply_patch 工具—— 把编辑表达为结构化补丁，而不是自由文本命令。

好处：降低「改错文件」的概率。补丁要么对得上，要么直接失败。

路线 B本书 / 多数 Agent

显式：读写编辑各占一个工具

保留单独的 Read / Write / Edit，工具边界清晰，模型一眼能看出「我现在是要读、要覆盖、还是只改一段」。

本书选七个，是为了让读者看清 Coding Agent 到底需要哪些基本能力。

结论：七个不是标准答案，是一个「可读性优先」的教学切分。 真正的设计问题是——哪几个原子动作必须被显式建模，才能让模型不犯错。 一旦你的沙盒里能跑 bash，六个、七个、三个都能工作，区别只在出错时的可恢复性。
5.1.1 · 与第四章对齐/别把两套分类搞混

七个工具，只覆盖了五类通用工具里的两类

第四章按调用方向和作用性质把工具分成五类；这里的七个是 Coding Agent 的 特有基础配置。两套分类维度不同，不要混着记。

第四章的五类七个工具中的对应说明
感知 Read · Glob · Grep 看文件、看路径、看内容。Agent 获取信息的全部入口。
执行 Bash · Code Interpreter · Write · Edit 跑命令、跑代码、改文件。Agent 改变世界的全部出口。
协作 — 多 Agent 之间的任务分派与结果汇总，本章不涉及（见第 10 章）。
事件触发 — 定时器、Webhook、异步回调（见第 6 章）。
用户沟通 — 提问、确认、展示产物。Coding Agent 通常直接对话，不需要专门工具。
一句话记住：七件套 = 感知 + 执行。它解决的是「Agent 能不能动手」， 不解决「Agent 怎么跟别人协作、怎么被叫醒、怎么跟人确认」——那三类是叠加在之上的。
5.1.1 · 为什么值得做/四个真实场景

代码不是「写程序」，是通用的问题解决手段

为什么每个通用 Agent 都该有 coding 能力？因为这四种情况，你迟早会撞上—— 而它们都不在「编程」的语境里。

01思考

数学推理算得准，不是算得像

写段代码交给求解器，拿精确答案，而不是靠模型「心算」。模型的思考是概率性的，数学要的是确定性的。

02约束

固化业务规则7 天到底是几天

「购买后 7 天内可退款」——自然日还是工作日？下单时间还是发货时间？代码没有歧义。

03扩展

临时造工具缺什么就写一个

工具箱不必预先穷举。遇到没见过的需求，当场生成一个小脚本补上缺口。

04适应

格式变了动态生成解析逻辑

上游接口字段漂移，等人改代码要排期；让 Agent 看着样本现场写解析，几分钟适配。

这就是「元能力」的雏形：工具箱里只有七个简单工具，但能力边界可以随时扩张—— 因为它能当场造出第八个、第九个工具。下一节 5.2 会把这六个方向完整展开。

CAP 01输入

问题来了：为什么核心是 Coding，而不是另外两个？

5.1.2 · 架构判断/几乎一切产出最终都落到代码

三种能力，一个内核

因为几乎所有高效的内容生成，最终都要落到代码上。 代码生成是效率最高、成本最低、可复用性最强的能力基座——另外两个能力，很多时候只是代码能力的「降级替代」。

WHY CODE IS THE CORE
// 三大能力各自的最优实现路径 Deep Research → 代码驱动的 Web 请求与解析 ✓ 最优 → 浏览器视觉操作 ✗ 慢 Computer Use → 调用 API / 写脚本 ✓ 最优 → 点鼠标、找坐标 ✗ 脆 Coding → 写代码 ✓ 唯一 // 结论：另外两个能力，最终都在调用它
  • 成本：一次 API 调用是几分钱，一次 GUI 操作是几十秒的视觉推理。差两个数量级。
  • 延迟：代码执行毫秒级；Computer Use 要截图、要定位、要规划下一步。
  • 稳定性：接口签名稳定；界面改一版像素，鼠标坐标就全废。
  • 可复用：写下的脚本能存下来、能版本控制、能给别人用；一次成功的点击序列不能。
所以 Computer Use 不是不重要，而是「没有别的路时才走的路」—— 凡是能用代码或 API 完成的，都该用代码。用代码省下来的钱和时间，才是通用 Agent 能规模化服务的前提。
5.1.2 · 证据/你以为在生成内容，其实在生成代码

五种产物，底层全是代码

你以为 Agent 在生成它真正的代码形态为什么这件事重要
PPT / Word 文档 OOXML（Office Open XML） 本质是 zip 包里的一堆 XML。所以「改一页版式」= 改一段结构化代码，不需要视觉定位。
PDF 报告 Markdown / HTML / LaTeX 先写源码再编译。Agent 能精确控制分页、图表位置、字体层级。
数据分析与图表 Python 脚本 pandas 聚合 + matplotlib 绘图。数字由代码算，不经过模型「抄写」，所以不会抄错。
浏览器里的操作序列 可复用的 RPA 代码 一次成功的点击序列可以固化成脚本，下次直接跑，不必再付视觉推理的成本。
深度调研结论 Web 请求 + 解析代码 抓取、清洗、比对都由代码完成；模型只负责判断「哪些值得读」。
一句话：内容生成的天花板，不是模型的文笔，而是它能不能把意图翻译成一份可执行的、可验证的代码。 翻译得了，就能自动化；翻译不了，就只能靠人。

5.1.2 · 记忆层/为什么是 Markdown 而不是向量库

文件系统不只是存储，是记忆、知识和能力的中枢

MEMORY.md · 长这样
# 用户偏好 - 报告格式：PDF - 语言：中文 - 称呼：Bojie # 环境事实 - 数据源：Google Sheets ID: 1a2b3c... - 时区：Asia/Shanghai # 经验 - 该银行电话验证需要开户行地址 （2026-10-22 实测）

选择 Markdown 而不是向量数据库，看起来反直觉，实际上极其有效：

  • 用户能直接读、直接改。Agent 记错了某件事？打开文件删掉那一行就行——不需要「重训」，也不需要写一条纠正指令。
  • 天然保留时间顺序。按日期归档的日志，避免了语义检索里最常见的时间混淆（「上周说的」和「上个月说的」混在一起）。
  • 可以进 Git。版本控制、diff、回滚——记忆的每一次变化都可追溯。
更关键的一点：Agent 有写文件的能力，就意味着它具备了修改自身外部产物的技术条件。 第一次做某个任务时发现的新知识（比如「这家银行要开户行地址才能验证身份」），可以先写进记录—— 什么时候这条记录足够可靠、能升级成知识或程序，是第 9 章要讨论的持续进化问题。
5.1.2 · 别推过头/这个判断有边界

「Coding 是核心」只对开放任务型 Agent 成立

原文在这里做了一个重要的自我限定。如果你把它理解成「所有 Agent 都该以 Coding 为中心」，就会做错架构决策。

维度开放任务型通用 Agent垂直领域 Agent（如客服）
任务边界 不确定。任务千变万化，无法预先枚举所需工具 相对封闭。围绕固定业务流程、领域工具、对话策略构建
产物形态 多样：报告 / 表格 / 网页 / 视频 / 代码 稳定：回答、工单、退款单、订单变更
代码的角色 架构中枢——元能力，动态扩展能力边界最经济的路径 工具箱里的一件工具，不是架构中枢
代表 Manus、OpenClaw、Claude Cowork τ-bench 里的航空 / 电商客服 Agent
但注意后半句：即便在垂直 Agent 里，coding 仍是重要的基础能力—— 精确计算、数据处理、规则校验都离不开它。区别只是：它是「必备零件」，而不是「承重墙」。

5.1.3 · 项目文档化/第一件事不是改代码

第一天，不会直接提交代码

Agent 首次接触一个仓库，和新人第一天入职是同一件事：先熟悉环境，还是先改文件？

AGENT 的第一小时 · 只读
# 建立认知框架，而不是急着定位 01 目录结构 src/ tests/ docs/ 各放什么 02 模块边界 谁负责什么、谁依赖谁 03 核心抽象 被最多地方引用的那几个类型 04 指令文件 有没有 README / CLAUDE.md 05 测试入口 怎么跑起来，跑得起来吗 产出：一张「这个仓库怎么组织」的地图 然后：才决定改哪里、怎么改
  • 顺序不能颠倒。先目录、再模块、最后才是具体文件。反过来，就是从细节里爬不出来。
  • 先建模，再定位。没有全局地图的搜索，找到的永远是「看起来像」的那一处。
  • 这一步没有输出物。但它决定了后面五步的判断质量——读错结构，改得越快错得越远。
原文的类比很准：新工程师第一天不会提 PR。Agent 也一样，先读，再写。
5.1.3 · 项目文档化/文档缺失的时候

文档缺失，补文档是 Agent 自己的活

原文的措辞很硬：「不应在盲目状态下开始工作，而应主动承担文档化的责任。」

READ输入

系统性地读库

不是抽几个文件看看，而是按目录把仓库完整走一遍——先看目录树与入口文件，再顺着 import 往下钻。

PARSE识别

认出骨架

主要模块、核心抽象、组件之间的依赖关系。这三样是后面所有判断的地基：改哪里、会不会碰到别人。

WRITE产出

写一份初始文档

架构概览、目录结构、测试运行指南——给别人入门，也给自己当蓝图。写下来的那一刻，下一次任务就不必从零理解。

原则：知识的显式化是高效协作的前提。没写下来的理解，只有这一个 Agent 有，下一个还得重新读一遍。
5.1.3 · 项目文档化/仓库里的知识有两种读者

README 给人读，指令文件给 Agent 读

写给人的那份讲究叙事，写给 Agent 的那份讲究约束——两者的差别不在格式，在读者。

文件写给谁什么时候被读到
README.md 刚加入的开发者 第一次接触项目时从头读一遍；之后偶尔回来查命令。
CLAUDE.md · AGENTS.md · .cursorrules 本项目的 Agent 每次会话开始，自动注入上下文——不需要谁提醒它去读。
SOUL.md 跨项目工作的 Agent 定义「Agent 是谁」：身份与行为规则，换项目也不变。
MEMORY.md 同一个 Agent 的过去 每次开工前回读：跨会话沉淀的经验与用户偏好。
前两行在说「这个项目怎么干活」，后两行在说「这个 Agent 是谁、记得什么」——层次不同，但都是文件。
5.1.3 · 上下文工程/项目级的系统提示词

指令文件，是最经济的稳定前缀

CLAUDE.md · 一个真实的样子
## 构建与测试 用 pnpm test，不要用 npm test ## 代码风格 禁用 any 类型；组件一律函数式 ## 禁区 不要改动 migrations/ 目录 # 每次会话开始，整段自动进入上下文 # 相当于这个项目自己的系统提示词
  • 注入即前缀。不是每次对话里重复交代规矩，而是开工前它已经在上下文里了。
  • 稳定即便宜。内容不随任务变化 → 前缀命中 KV Cache，省的是钱，也是首字延迟。
  • 落地即原则。「知识必须存在于代码库本身」，这是它最直接的一种形态。
与 README 的真正区别不在形式：一个回答「这是什么」，一个回答「在这里该怎么干」。
5.1.3 · 项目文档化/什么样的仓库对 Agent 友好

好的仓库，让 Agent 读得到

第二章那条判断在代码库层面的落点：Agent 只能读到被写下来的东西，口口相传的规矩对它等于不存在。

知识该住在哪里
repo/ ├─ docs/adr/ # 决策：为什么选 A 不选 B ├─ .github/ │ └─ pull_request_template.md │ # 上下文：改了什么、为什么 ├─ CONTRIBUTING.md # 经验：环境、发布、踩过的坑 └─ CLAUDE.md # 约定：在这里怎么干活
  • 决策记录在文档里。半年后没人记得为什么这么选——Agent 更不可能从代码里猜出来。
  • 上下文写在 issue 与 PR 里。diff 只说「改了什么」，描述才说「为什么」。
  • 经验沉淀在开发者指南里。资深同事心里的那些坑，写下来才成为团队资产。
一个可操作的指标：一个远程新人，只靠代码仓库和文档，能不能独立开展工作。能，Agent 通常也能。
5.1.3 · 需求澄清/先判断该不该问

简单需求直接做，复杂需求先问

修一个已知的 bug、调一个参数——可以直接进入实现。但原文说，软件开发中大多数任务并非如此简单。

维度 01输入

需求本身的模糊

用户知道想要什么，但说不清边界；说出来的只是症状，不是目标。

维度 02路径

实现路径的多样

多条技术路线都可行，各有取舍，没有唯一正确的那个答案——选哪条取决于团队栈、维护成本和上线压力。

维度 03影响

影响范围的广泛

要改多个模块，可能顺手破坏现有功能——越自信越危险，所以越要先有人确认边界。

碰上任一条：先做探索性调研把边界澄清，必要时主动与用户对话。在模糊状态下动键盘，返工的成本远高于多问一句。
5.1.3 · 需求澄清/一句话需求里的三个洞

「优化系统性能」，到底指什么

澄清对话 · 三问三答
用户：优化一下系统性能 Agent 追问 ① 目标 响应时间 / 内存 / 吞吐？ → 接口 P99 从 800ms 降到 200ms ② 权衡 能改接口吗？能牺牲易用性吗？ → 接口不能动，加缓存可以 ③ 瓶颈 profile 过吗，还是凭感觉猜？ → 先跑一轮 profile 再谈方案
  • 三问答完，「优化」才可验证。P99 降 75%、接口不动、允许加缓存——这才是一个能验收的目标。
  • 少问一条，方案就偏。换了接口、动了易用性，指标却纹丝不动，是这类需求最常见的结局。
  • 能自己查的别问人。profile、日志、慢查询 Agent 可以自己跑；查不到的取舍才值得打断用户。
在需求模糊的状态下开始编码，往往导致大量返工——返工的不是代码，是方向。
5.1.3 · 设计文档/人类的介入点

设计文档不是交付物，是换一次审查的接口

DESIGN.md · 四个必答问题
# 一页纸，回答四件事 ① 修改哪些模块，为什么是它们 ② 采用什么方案，相对优势在哪 ③ 需要引入哪些新依赖 ④ 预期对系统的影响 # 写完 → 提交人审 → 批准 → 才动手
  • 写的过程就是预演。很多方案在画调用链的时候就被自己否掉了——那时还没花一行代码的成本。
  • 审查成本差两个数量级。一页文档能看出方向对不对；三百行 diff 只能看出细节对不对。
  • 所以它是一道闸门。Agent 提交设计文档，等批准，再继续；批准之前不动键盘。
这是整套流程里最划算的一次人工介入：花十分钟读一页纸，省下的是几百行的返工。
5.1.3 · 实现与验收/由验证判定何时可以停

完成的标准是测试通过，不是代码写完

设计获批之后才动键盘。而代码写完，只走到了一半——剩下的一半由测试来判定。

01

按规范实现

遵循项目代码规范，复用已有抽象和工具；不为这次任务另造一套写法，必要时做适度重构。

02

写测试

覆盖正常路径、边界条件、异常情况——而不是只测一遍「能跑通的那条路」。

03

跑测试，进入「测试-修复」循环

失败不是上报：读报错、定位、改代码、重跑。这个循环可能转好几轮。

04

修到全绿

迭代到全部通过为止。这一刻才算「完成」，也才是可以交给用户的那一刻。

最常见的偷懒：写完代码不跑测试，直接报「任务完成」。把「测试通过」当作完成标准， 正是 Loop 工程「由验证判定何时可以停」在编码场景的落地。
5.1.3 · 自我审查/测试全绿之后还没完

绿了之后，换一副眼睛看代码

自审清单 · 五个问题
# 测试全绿之后，逐条过一遍 [ ] 可读性 命名和结构，别人能看懂吗 [ ] 注释 写的是「为什么」，还是「做了什么」 [ ] 性能 有没有 N+1、有没有重复计算 [ ] 安全 输入校验、权限、注入面 [ ] 风格 和项目既有写法一致吗
  • 重读代码。不是扫一遍 diff，是按「第一次看这段代码的人」的角度读。
  • 跑 lint 与类型检查。机器能查的那部分，不要浪费人的注意力。
  • 调一个审查子 Agent。换一份上下文重新读，比同一份上下文自己夸自己有效。
分界线很清楚：审查发现问题，就回到修改阶段；把有缺陷的代码交出去，前面那些绿测试等于白跑。
5.1.3 · 文档同步/什么时候必须改文档

过时的文档，比没有文档更糟

没有文档，读者知道自己在猜；过时的文档，读者以为自己在读事实——它会误导后来的开发者。

变化 01结构

引入新模块

目录和职责变了，架构图上的框就对不上现实；新同事按图找代码，会找到一片空白。

变化 02依赖

依赖关系变化

谁调用谁变了，照着旧图找代码就会走进死路——拆分层、换中间件这类大动作最容易留下这种图。

变化 03语义

核心抽象改语义

名字没变、行为变了——签名一样，返回值的意思变了，比直接报错更难查。

这套流程的三条原则：计划先于行动（先设计再编码）、验证贯穿始终（测试与审查）、文档与代码共同演化（改完就同步）。
5.1.3 · 现实中的裁剪/推荐流程不是必选流程

同一套流程，不同模型裁剪的位置不一样

SIMPLE跳过

简单 bug 修复

直接进入实现，跳过设计文档；但测试这一步仍然要跑。

COMPLEX完整

复杂且影响面大

六个阶段一个不落，设计文档必须先过人类审查。

动手之前先调查型先提交型
读多少 目录、实现、调用方、测试，读到能画出调用链 只读少数最可能相关的文件
什么时候动手 想清楚再写，第一次提交就接近正确 先提交补丁，把编译与测试的报错当作调查

换 Harness，这个阈值可能不变；同一个 Harness 里换模型，它又可能变——
它首先是模型学到的行为策略，不是 Coding 产品的界面风格。

Harness 的提示词、工具和预算能放大或抑制它，但不必是它的来源。第七章在固定 Harness 里衡量这一差异，第八章再从后训练角度解释。
5.1.4 · Harness 工程/先把定义对齐

Harness 不是模型外面的一圈，它就是公式的另一半

第一章给过 Agent = Model + Harness。这里的 Harness 不止上下文和工具，还包含约束、验证、纠正——五样凑齐，才是一套完整的 Harness。

为什么先讲 Coding：代码任务的可验证性在所有 Agent 任务里最高，约束、验证、纠正三样都有现成基础设施可以依托—— 这是 Harness 红利最大的一个领域。
5.1.4 · 四件组件/缺一件就漏水

稳定不稳定，看的不是模型，是这四件东西

第一章的第二层，落到 Coding 场景就是四件可以逐条检查的工程组件——没有一件属于模型。

01验收基线

什么算做完了

测试套件、CI 管道、代码审查标准。把「做完了」从一个感觉，变成一次跑得出结果的检查。

02执行边界

能碰什么、不能碰什么

模块边界、依赖规则、权限控制。哪些目录、哪些接口不在可写范围里，写清楚。

03反馈信号

自动化的对错判断

Linter 输出、测试结果、类型检查错误。对错当场由机器判，不等人类说一句「不太对」。

04回退手段

出了问题怎么恢复

Git、沙盒隔离、快照回滚。做错了能一步退回去，它才敢试错。

分工：验收基线和执行边界负责「说清楚」——什么算对、什么不许碰； 反馈信号和回退手段负责「拉回来」——跑偏了当场发现，砸了能退回上一个好状态。

Coding 天生站在最好的那个象限

两个维度切一刀：目标清不清晰、结果能不能自动验。四块地的瓶颈完全不同。

5.1.4 · 往哪推/四个瓶颈不一样

Harness 唯一的目标，是把任务往左上角推

四个格子的瓶颈不一样，所以「换一个更强的模型」只对其中一格有效。

一句话记住：加模型只解第一格；剩下三格要靠补验收标准、补人工吞吐、补目标定义——这些全是 Harness 的活。
5.1.4 · 成熟度的来源/不是代码模型特别强

Coding 成熟度最高，不是因为代码模型特别强

而是因为软件工程几十年攒下的基础设施，天然就是一套强大的 Harness——它们本来不是为 Agent 造的。

早就存在的设施 在 Harness 里担任 它本来是为谁造的
测试套件 · CI 验收基线 + 反馈信号 为「改代码别改坏」
Linter · 类型检查 反馈信号 为把规范写成可执行的规则
Git 分支 · 回滚 回退手段 为多人协作与合并
权限 · 模块边界 执行边界 为团队分工与隔离
可以迁移的判断：一个领域能被 Agent 自动化的程度，取决于它的「错」能不能被机器判定。 判得了，就能交给 Agent；判不了，模型再强也只能等人。
5.1.4 · 案例一/大规模代码迁移

大规模迁移赢在 Harness，不在模型

一家大型科技公司公开分享的迁移实践：任务量以万计，人不可能逐个看。真正的杠杆是三件 Harness 上的事。

01知识

知识必须活在代码库里

迁移规则、目标写法、历史先例都写进仓库里的文件。Agent 看不到的，等于不存在——开会讲一遍不算。

02约束

约束编进 Linter 和 CI

不写成文档等人自觉。规则一旦进了流水线，写法不对就提交不上去——不需要谁记得住。

03闭环

验证与纠正全链路自动

改完自动跑测试，报错自动回改，直到整条链路转绿。人只在最后抽样，不在中间守。

换个说法：知识若只存在于某个人嘴里，Agent 的规模上限就是那个人的时间。 把知识搬进仓库，才是「一万个文件」和「一百个文件」的区别。
5.1.4 · 案例二/LangChain

一行模型都没换，基准分数照样涨

只优化 Harness 的三个面——系统提示词、工具中间件、自验证循环——基准任务表现就显著提升。

01说清怎么干

系统提示词

任务边界、输出格式、什么时候该停下来问人。把默认做法写死，不让模型每次自由发挥。

02工具护栏

工具中间件

参数校验、失败重试、结果裁剪。脏数据在进上下文之前就被挡住，模型看不到，也就不会被它带偏。

03交卷前自查

自验证循环

交卷之前先跑一遍检查，不合格就自己重来。把「发现问题」提前到还没交出去的时候。

更值得抄的是方法论：用 Agent 去分析失败轨迹，再从轨迹里改 Harness。 这一步让 Harness 工程从「老师傅凭经验」，变成「看数据改配置」。
5.1.4 · 案例三/Anthropic 的长任务

长任务的两个老毛病，用两个角色治

一次想做太多、过早声称完成——这是长时运行 Agent 最常见的两种失败，也都不是模型能力问题。

TASKS.md · 跨轮次传递的中间成果
# 初始化 Agent 产出，执行 Agent 维护 [x] 01 抽出公共鉴权模块 [x] 02 迁移 user 服务 [ ] 03 迁移 order 服务 ← 下一轮从这里继续 [ ] 04 补集成测试 [ ] 05 删除旧鉴权代码 # 已完成的代码文件也在仓库里 services/order/ 已改 4 个文件
  • 初始化 Agent 只管拆。把大任务分解成一份可勾选的清单，先想清楚再动手。
  • 执行 Agent 只管推。一次只做清单上的一行，做完打勾，接着下一行。
  • 中间成果留在文件里。已改的代码、更新后的清单，下一轮直接接着用——不靠上下文记。
两个毛病各有一味药：拆清单治「一次想做太多」，清单上没打勾就不算完治「过早声称完成」。
5.1.4 · 收束/三个案例对位

三个案例，改的是同一个位置

都不是让模型更聪明，而是把「对不对」的判断权，从模型手里挪到基础设施手里。

案例 主要动了哪件组件 挪走了什么判断
大规模迁移 执行边界 + 反馈信号 规则从文档挪进 Linter 与 CI，写错就提交不上
LangChain 反馈信号 + 纠正 「哪里错了」改由失败轨迹来说，人只看轨迹
Anthropic 验收基线 + 纠正 「做完了」改由清单和文件说，模型无权宣布
一个可检验的推论：判断权一旦交出去，换不换模型就没那么要命了。 这也解释了为什么三个案例的收益，都不来自换一个更强的模型。
5.1.4 · 原则一/约束优先于指导

能强制的就别只建议，差别是「做不了」

能用代码强制的规则，就不要写成文档建议。前者是「做不了」，后者只是「建议别做」——中间隔着一整次模型自觉。

把一条口头规范改成一条检查
# 改造前：写在文档里，靠人看 PR 「禁止直接 import requests， 统一走 http/client.py」 # 改造后：写成一条会失败的检查 ci/lint.sh grep -rn "^import requests" src/ \ && exit 1 # PR 直接红，Agent 也读得到这行报错 # 附带效果：改完当场知道，不用等人说
  • 最小可执行的改造动作：翻出团队规范里最常被违反的一条，把它写成一条 lint 规则或一个 CI 检查。
  • 差别在长任务里会被放大。「做不了」一次生效；「建议别做」每一步都要重新赌一次模型的自觉。
  • 提示词该留给别的事：什么时候该停下来问人、输出成什么形状——这些本来就写不成检查。
判断标准很简单：这条规则，能不能写成一条会失败的检查？能，就别只写进文档。
5.1.4 · 原则二、三/验证与反馈

人工审查是瓶颈，而且反馈太慢

验证要自动化，因为人工审查不可扩展；反馈要快、要结构化，因为越接近出错时刻，纠正越省事。

维度 人工审查 自动化验证
吞吐 天花板是审查者的时间 与任务量无关，可以并行
延迟 几小时到几天 秒级，改完立刻出结果
判法 换个 reviewer 换一套标准 同一条规则，每次同一种判法
信息量 一句「这里不太对」 文件:行号 + 错误码 + 期望值
第二章的 Agent 状态栏就是这条原则的界面化：详细错误信息、工具调用计数器—— 把「哪里错了、错了几次」直接摆在模型面前，而不是让它自己猜。
5.1.4 · 原则四/回退与过程性错误

结果对不算完，过程错也是失败

回退要可靠——错误可逆，Agent 才敢大胆试错。而验收基线管结果，执行边界管过程：用错方法达成，同样是失败。

两条破坏性捷径 · 验收指标全绿
# 反例 1 · 修数据库连接故障 Agent → 把库删了，重新建 服务恢复 ✓　数据没了 ✗ # 反例 2 · 修编译错误 Agent → 删掉整个文件，重写 编译通过 ✓　实现没了 ✗ # 两单任务，验收指标都是绿的
  • 回退是试错的前提。Git 分支、沙盒环境、快照回滚——任何错误都可逆，它才敢动手。
  • 但指标挡不住捷径。把限制写进最终评估指标，Agent 也常能找到绕过去的办法，这就是 reward hacking 的日常形态。
  • 所以对动作设闸门。rm -rf、删生产数据、覆盖未读文件，执行前审批——约束的是动作，不只是结果。
一句话：结果指标是事后审计，动作审批是事前闸门。前者挡不住有意绕路，后者能—— 本章安全一节的语义解析、第四章的 Sidecar 复核，做的都是这道闸门。
5.1.4 · 工具编排/故障边界控制

一个工具挂了，不该带走整批任务

并行调用下，Harness 要回答一个模型不会回答的问题：一个失败，要不要连坐？

这就是反面教材的镜像：「一个命令失败，整个任务中止」是最脆的那种 Harness。 边界划对了，局部失败只是数据；划错了，一次网络抖动就能报废整轮工作。
5.1.5 · 故障与错误恢复/三个问题，一条线索

故障恢复，才是真正的分水岭

上一节给的是原则与组件；这一节把它们放进真实故障里跑一遍。 三个问题，顺序不能换：先分类，再检测，最后才谈恢复与终止。

Q1分类

会遇到哪些故障

API、工具、上下文、控制流四层。层不同，处置手段完全不同——不能都用一句「重试一下」打发。

Q2检测

怎么发现它坏了

单次错误只看类型；真正该盯的是重复调用指纹与连续失败次数——那是行为出了问题。

Q3终止

什么时候必须放手

恢复机制自己也会失效。每条恢复路径都要有上限，「什么时候停」和「怎么救」同样重要。

问题的严重性，第一章已经演示过：仅仅缺失一条工具结果反馈，就足以让 Agent 陷入无限循环。 真实生产里的故障只会更多样，所以这一节从分类讲起。
5.1.5 · 故障分类学/先分类，再谈处置

按发生的位置，把故障切成四层

这是系统应对的第一步。分类不是为了归档，而是为了选手段——同一句「重试一下」，在四层里的含义完全不同。

L1基础设施

API 层API LAYER

限流、过载、超时、断连、输出截断。任务可能完全正确，是基础设施在报错。

L2手脚

工具层TOOL LAYER

幻觉调用、参数畸形、执行抛异常。错在Agent 伸出去的那只手。

L3记忆

上下文层CONTEXT LAYER

窗口溢出、压缩失败、轨迹结构损坏。错在喂给模型的那段历史。

L4循环

控制流层CONTROL LAYER

死循环与死亡螺旋。错在Agent 自己的下一步，外部环境其实正常。

分层的用处很直接：前两层多半靠「等」或「改输入」，后两层必须靠「打断」。 把四层混成一类，就只能一律重试——而重试恰恰救不了后两层。
5.1.5 · API 层/与任务内容无关

API 层的故障，不说明任务做错了什么

它只说明「这一次请求没被服务好」。所以在这一层里改任务、改提示词，都是无效动作。

API LAYER · 五种噪声
429 Too Many Requests ← 配额用尽 503 Service Unavailable ← 上游过载 — request timeout ← 链路太慢 — connection reset ← 连接被掐断 — finish_reason=length ← 输出触顶 # 任务没变、提示词没变，重发还是同样的结果
  • 共同点：与任务内容无关。换一个任务、换一句提示词，这些错误照样出现。
  • 所以有效的动作只有两个：等（退避之后再来），或者改请求（上限、模型、区域）。
  • 但「可重试」不等于「原样重试」。输出触顶也能再发，前提是先把上限提高，或从断点接续。
把它当噪声，还有个隐性好处：不用去怀疑模型的判断——在错误的地方调提示词，是最常见的排查浪费。
5.1.5 · 工具层/三种畸形，一种循环

三种单次事故，和一种行为模式

前三种错在「这一次调用」，装成工具结果喂回去，模型下一轮就能自己改； 最后一种错在「反复做同一件事」。

01幻觉

幻觉调用HALLUCINATED CALL

调用了不存在的工具。错不在参数，在它以为这个工具存在。

02约束

参数畸形MALFORMED ARGS

不符合输入约束——该给对象，却给了字符串。模型知道要做什么，只是写错了。

03运行

执行抛异常EXECUTION ERROR

工具真的跑了，但中途失败。以上三种，都可以装成一条工具结果返回。

04最危险

同错重试RETRY LOOP

工具反复返回同一个错误，模型不加改变地反复重试。这不是事故，是行为模式。

两类故障，两种治法：单次事故靠「更具体的错误信息」就能治； 行为模式不行——错误早就返回了，模型只是没改，它需要的是计数器，而不是再重试一次。
5.1.5 · 后两层/错在 Agent 自己

后两层不是环境坏了，是 Agent 自己坏了

请求发得出去，工具也跑得动。坏的是它对历史的记忆，和对下一步的选择——外部一切正常，对话却已经走不下去。

L3记忆

上下文层CONTEXT LAYER

窗口溢出、压缩失败、轨迹结构损坏——比如工具调用缺少配对的结果消息。错在「模型看到的历史」，不在模型本身。

L4循环

控制流层CONTROL LAYER

死循环是反复执行相同操作却毫无进展；死亡螺旋是恢复逻辑自己又调 LLM、再次出错、连锁反应。错在「Agent 的下一步」。

COMMON处置方式

共同点：越「努力」越糟——所以不能等，只能打断

前两层还能换一种输入来修；后两层继续跑下去，只会烧掉更多 token，把错误固化成更大的错误。

这就是分类的价值：同样是「失败了」，L1 该退避、L2 该改参数、L3 该压缩或修复轨迹、L4 该直接终止这条路径。
5.1.5 · 检测/先判断值不值得

先问「值不值得」，再决定怎么重试

捕获故障后的第一个判断，不是「要不要重试」，而是「原样重发，会不会得到不同结果」。

捕获到的故障可重试？该做什么
限流 429 · 服务过载 · 网络抖动 可重试 同一个请求，退避之后再发——退避要叠加随机抖动。
输出触顶被截断 可重试，但请求要变 先提高输出上限；仍不够，就在末尾追加元指令从断点接续。
参数不合法 · 参数畸形 不可重试 原样重发多少次都是同样结果，必须改输入。
权限不足 · 工具不存在 不可重试 改策略：升级人工，或把结构化错误喂回给模型。
所以生产级 Harness 维护的是一张「错误 → 恢复策略」映射表，而不是一句笼统的「出错就重试」。 可重试与不可重试的分界线，就是「重发会不会有信息增量」。
5.1.5 · 检测模式/单次之外看模式

比单次错误更该盯的，是重复出现的模式

单次错误告诉你「哪里坏了」；重复出现的模式才告诉你「它已经修不好了」。 两个计数器，盯的都是后者。

01指纹

重复调用指纹CALL FINGERPRINT

对「工具名 + 参数」算指纹。同一指纹反复出现，说明它在原地打转——第一章消融实验里反复调同一工具，正是这个模式。

02计数

连续失败计数FAILURE COUNTER

每条恢复路径各记一本账：压缩、权限询问、输出接续分别计数。混在一起，一条路径的问题会污染另一条的判断。

03去处

为熔断提供依据CIRCUIT BREAKER

计数不是为了统计，是为了在「再试也没用」那一刻之前停手。阈值一到就掐断这条路径，把配额留给别的办法。

这两个机制都不需要模型参与：它们跑在 Harness 里——所以模型「觉得自己还在努力」的时候，外面已经能判定它卡住了。
5.1.5 · 活性监控/连接在，数据不来

最危险的失败不是断开，是静默卡死

断开至少会立刻报错；静默卡死不会——连接建立成功，数据流却停了，像水管通着但不出水。

STREAM · 连接正常，数据停了
[00:00] connect 200 OK ✓ [00:01] chunk 「分析这个…」 ✓ [00:02] chunk 「仓库的…」 ✓ [00:47] — 无新字节 ? [00:48] sdk timeout — ✗ 不触发 [00:49] watchdog idle > 20s ✓ 判定卡死 [00:50] kill stream → 触发重试
  • SDK 的超时往往只管建连。连上之后就不再计时，传输停住它也不会报错。
  • 所以要独立的空闲看门狗（watchdog timer，超过设定时间没有新输出就判定卡死），而不是复用连接超时。
  • 超时之后要主动杀死挂起的流，再触发重试。挂着的流不释放，重试只会让并发越叠越高。
可推广成一条原则：每个长连接都需要活性信号，而不能只依赖连接超时。
5.1.5 · 完整性监控/结构坏了，先修再喂

轨迹缺了配对，要在注入之前补好

工具调用必须有配对的结果消息；缺了，模型看到的就是一段自相矛盾的历史。 修复发生在注入上下文之前，而不是把结构异常抛给模型或用户。

MODE 01产品

产品模式PRODUCT · 宽容

缺哪条结果，就补一条占位消息，让轨迹保持结构完整。用户不该因为一个内部结构问题被打断。

MODE 02训练

训练数据收集TRAINING · 严格

拒绝修复：合成占位符会污染训练数据——模型会学到「结果可以是编的」。宁可丢弃这条样本。

「产品模式宽容、训练模式严格」：同一个修复动作，在产品里是兜底，在训练里是污染。 这条双重标准，体现的是 Harness 与模型训练的深度耦合。
5.1.5 · 恢复/按对用户透明的程度分级

能用低一级的手段，就不要升级

分完类、计完数，才轮到「怎么救」。三级手段按对用户透明的程度排列， 判断标准只有一条：这一级能不能自己把问题吃掉。

01

静默重试

同一个请求，退避之后再发，对用户完全不可见。升级条件：重试用尽仍失败。

02

降级与接续

改变请求本身再试：提上限、换模型、换模式。升级条件：怎么改都不通。

03

暴露给用户

所有自动手段用尽，才呈现错误并附上已尝试的动作。这里没有下一级。

VISIBILITY · 用户视角
# 用户能感知到哪一层 L1 静默重试 （看不见） L2 降级 · 接续 （看不见） —— 以上都在扣留错误 —— L3 暴露错误 一条完整说明 # 越往下，代价越高 # 时间 → 请求 → 用户重新理解
SUMMARY分级的意义

大多数故障停在第一级，第二级是例外，第三级是兜底

每升一级，代价就翻一倍：第一级只花时间，第二级要改请求，第三级要用户重新理解任务。

5.1.5 · 静默重试/两个细节决定成败

「失败就重试」有两个坑

同样是重试，退避策略没做对会制造二次拥塞；调用优先级没分清， 后台重试会挤占主链路的配额。

RETRY POLICY · 退避与抖动
# 两个细节都在这几行里 for attempt in 1..N: if not retryable(err): break wait = min(cap, base * 2 ** attempt) wait += random(0, jitter) # 抖动 if err.retry_after: # 服务端提示 wait = max(wait, err.retry_after) sleep(wait)
  • 抖动不是装饰。纯指数退避会让所有客户端在同一毫秒发起第 N 次重试；随机抖动把这一批打散，否则重试本身就是一次小型 DDoS。
  • 服务端说了算。返回里带等待时长时，就按它来——那是对方最清楚自己什么时候能缓过来的时刻。
  • 前台重试，后台放弃。主循环的请求失败要重试；标题生成、输入建议这类辅助调用失败直接丢掉。后台重试挤占的是主链路的配额，这叫重试放大。
重试放大的可怕之处：它不报错。用户只会觉得「今天这个 Agent 有点慢」， 而账单和限流额度已经在后台被一堆没人看的标题消耗掉了。
5.1.5 · 降级与接续/改请求本身再试

重试无效，说明问题不在「什么时候发」

而在「发什么」。这一级的动作是改变请求的形状：改上限、改模型、改模式——三个最常见的场景。

01输出触顶

被长度限制截断OUTPUT TRUNCATED

先静默提高输出上限重发；仍不够，就在消息末尾追加一条元指令，让模型从断点接着往下写。

02主模型过载

降级到备用模型FAILOVER

但先剥离旧模型私有的格式块——否则新模型解析不了历史消息，降级当场失败。

03成本模式

高成本模式被限流RATE LIMITED

暂时回落到标准模式。先用可接受的答案把这一轮跑完，质量优化留到配额恢复之后。

三件事的共同点：改的不是重试次数，是请求本身。 所以这一级必须知道「这次失败到底缺什么」——只看到 429 就降模型，等于用更大的代价换一个不相干的答案。

顺序不能反：先提上限再谈接续，先剥格式再谈换模型。 跳过前置条件直接降级，是把一次可恢复的失败变成一次不可解析的失败。
5.1.5 · 最后一级/所有自动手段用尽之后

最后一步，才是让用户看见

不是一句「出错了」，而是一份交接单：我试过什么、走到哪一步、你接手时能从哪儿继续。

ERROR · 呈现给用户的样子
任务未完成：修改 src/db.py 时连接超时 # 已尝试的恢复（按顺序） 1. 静默重试 3 次 · 指数退避 2. 降级到备用模型 3. 压缩上下文后重发 ✓ 4. 跨厂商接管 ✗ # 建议的下一步 - 文件较大，可拆成两次编辑 - 或先只读，产出一份补丁
  • 位置。明确停在第几步，而不是笼统的「失败了」——用户才知道该从哪儿重来。
  • 动作。列出已经试过的恢复路径，避免用户重复你已经做过的事，也避免他误以为你没试。
  • 出口。至少给一条可执行的下一步：拆小任务、换模式、只读产出补丁。
前两级对用户完全不可见。这不是体验打磨，而是「恢复期间扣留错误」这条工程纪律的直接结果—— 下一页把它讲成一条通用原则。
5.1.5 · 工具层/错误变成模型的输入

工具层错误不终止会话

幻觉调用、参数不合法、执行抛异常——这些错误若抛给用户，任务就死在这里； 喂回给模型，下一轮还有机会自己改。

TOOL RESULT · 错误也是结果
# 模型幻觉调用了一个不存在的工具 工具返回 { "ok": false, "error": "tool_not_found", "tool": "read_dir", "available": ["read","write","edit", "glob","grep","bash"] } # 它和正常结果没有区别 # 只是 content 里的一段 JSON
  • 幻觉调用。收到「工具不存在」的结构化结果，并附上真实可用的工具清单——它下一轮就知道该用哪个。
  • 参数校验失败。错误里带上输入约束：哪个字段、什么类型、取值范围。只说「参数错误」等于没说。
  • 畸形参数。本该是对象却给了字符串，这类在执行前先做程序化修复，修不好才作为错误返回。
这是「反馈越结构化越好」的直接应用：喂回的错误越具体，模型自我纠正的成功率越高； 一句「调用失败」，只会让它把同一个错误再犯一次。
5.1.5 · 核心原则/边界是整个恢复循环

错误处理的边界不是单次请求

是整个恢复循环。在确认无法恢复之前，中间错误不该让消费者看见——无论是用户，还是订阅事件的下游系统。

这就是第一章那条纠正原则的工程化：在确认无法恢复之前，不暴露中间态。 恢复成功，消费者毫无感知；全部失败，才统一呈现一次。
5.1.5 · 跨厂商接管/把没跑完的轨迹交给另一家

能带走的是文字，带不走的是凭证

主模型持续不可用时，要换一家把这条轨迹接着跑完。障碍不在接口地址， 而在轨迹里有一部分东西只属于原厂商。

THOUGHT · 一段思考的两个部分
[thought] text 「先读 package.json 看脚本」 signature 厂商签发的凭证 ✗ 换家即失效 [tool_call] name read args {"path": "package.json"} [tool_result] ref call #1 # 工具调用：结构不同，语义一致 # 按目标厂商重新渲染即可
  • 工具调用好办。各家字段名不同、嵌套不同，但「调了什么、参数是什么」的语义一致，重渲染就行。
  • 难办的是思考。它由可读的文字与厂商附上的凭证构成——凭证用来证明这段思考确实出自它自己。
  • 换一家，文字照读，凭证作废。这就是接管的可行边界：搬得动的是内容，搬不动的是身份。
一句话记住：跨厂商接管的边界，就是「可移植的文字」与「不可移植的凭证」之间那条线。 后面所有的工程动作，都是在这条线的两侧做取舍。
5.1.5 · 凭证/三家三种态度

各家要求不同，方案按最严的一端设计

从「根本不校验」到「拒绝一切非自己签发的」，中间还有把凭证挂在工具调用上的——同一份轨迹，三种反应。

接收端对凭证的态度你的对策
宽松 不做校验，思考与凭证都照收 直传能过，但别把它当成通用方案
中等 校验签发方，外来凭证一律不认 丢弃凭证，文字以普通内容身份带入
严格 凭证还挂在工具调用上，删思考不管用 把历史调用改写成文字叙述，只求能接着跑

所以「把思考删干净就安全了」这条看似稳妥的策略，在严格的一端反而通不过—— 它删的是文字，凭证还在调用上。

退路要提前想好：历史工具调用改写成文字叙述后，模型不再把它当作真正调用过的工具， 但它至少能接着往下跑——这就是「降级到能跑」，而不是「保证无损」。
5.1.5 · 中立格式/可移植的留下，不可移植的标出来

轨迹不该按任何一家的接口格式存储

既然换厂商时必然要重写一遍，不如一开始就存成中立的——四种字段，一条原则。

NEUTRAL · 一条中立记录
{ "role": "assistant", "thought": { "text": "先读 package.json", "sig": null # 切换时丢弃 }, "calls": [ {"name": "read", "args": {"path": "package.json"}} ] } # 标识符在渲染成请求时才生成
  • 思考拆两半。文字是可移植的，凭证不是——存的时候分开，切换时只丢后半。
  • 调用只记名称与参数。不记厂商的 call id，标识符在渲染成具体请求时按目标厂商重新生成。
  • 文字当普通内容带入。不塞回目标厂商放思考的位置——那不是它的思考，它会拒绝。
  • 摘要本来就是副本。厂商返回的思考摘要，正是为这种场合准备的可移植版本，留着即可。
它的价值不止故障切换：第七章的评估重放、第八章的训练样本构造、第九章的经验提取， 依赖的都是同一份产物——中立格式是这套系统的公共底座。
5.1.5 · 实验 5-1/难度 ★★★

实验 5-1：换一家，把没跑完的轨迹接着跑

目标：验证中立格式能否让跑到一半的 Agent 换一家接着跑完，并量化「原样直传」与「一刀切剥光」的代价。

01设置

在哪儿切换SETUP

任务需多轮工具调用；中途注入连续的限流与过载，熔断后切换。选三家线上格式互不相同的厂商，两两切换。

02对照

三种做法METHODS

直传 原样搬进新结构
剥离 删掉全部思考与凭证
中立 只丢凭证，文字照带、标识符重渲染

03验收

拿什么比METRICS

首个请求留原始响应，失败必须是厂商真实报错。比完成率、切换后重复调用同一工具的次数、额外轮数与 token。

三种做法的差别只在「换手时丢掉什么」：直传不丢、剥离全丢、中立只丢凭证。 其余变量——任务、断点位置、目标厂商——必须完全一致，否则数字没有意义。

验收里有一条逆向要求：若中立做法在「重复调用」上并未优于剥离，同样如实记录。 实验的职责是给数，不是证明观点。
5.1.5 · 实验 5-2/难度 ★★

实验 5-2：输出断在一半，怎么接

目标：比较「整轮重发」与「以半截输出为前缀续写」，在成本、正确性与副作用上差多少。

01断点

切在三个位置BREAKPOINTS

在流式响应上分别切断：思考中途、正文中途、工具调用参数中途。三个位置坏的形状完全不同。

02三种接法

怎么续RECOVERIES

丢弃整轮重发；半截作为末尾 assistant 消息要求接着写；追加元指令说明从断点继续。半截调用要先转成文字再补完。

03验收

记四个数METRICS

恢复成功率、相对整轮重发省下的输出 token、补完后参数的合法率与语义正确率、重复副作用次数。

前三项是成本账，第四项是安全账：省下来的 token 一旦换来一次重复执行，就是负收益。

判分点在最后两项：合法不等于正确——拼接处常多出空白或重复字符； 而重复副作用，一次就够毁掉整轮结果。续写前按「工具名 + 参数」指纹去重。
5.1.5 · 熔断/每条恢复路径都要有上限

阈值从生产数据来，不靠拍脑袋

恢复机制自己也会失效，所以每条路径都要封顶。上限设成几，不该由直觉决定。

01上下文

压缩封顶COMPACTION

连续失败若干次就放弃压缩，改用硬截断。继续压缩只会把上下文越压越坏。

02权限

分类封顶PERMISSION

权限分类连续失败，就回退到人工询问。分类器不确定时，问人比猜便宜。

03输出

接续封顶CONTINUATION

续写最多尝试固定轮数，到点停手，把半截结果交出去。续到第 N 轮还断，说明接续解不了。

THRESHOLD这个「3」从哪来

连续 3 次CLAUDE CODE · 上下文压缩熔断

真实会话统计：曾有一个会话在这条路径上连续失败三千余次；这类无效重试每天在全球浪费约 25 万次 API 调用，逾千个会话出现过 50 次以上连续失败。

3 次是拐点，不是最优解：它落在「绝大多数故障在此之前已恢复」与「继续重试基本无望」之间—— 有数据支撑的解，比拍脑袋的解更容易在下一次事故里被辩护。
5.1.5 · 终止/单点熔断之外，还有连锁

死亡螺旋：恢复逻辑自己也会故障

单点熔断管一条路径的失败次数；死亡螺旋管的是路径之间——恢复动作触发的错误，又去触发同一个恢复动作。

上下文溢出，Agent 停止

02

停止钩子被触发

「结束时自动提交代码」——结束时自动执行的清理逻辑。

03

钩子调用 LLM 写 commit message

本来只是补一句说明。

04

又撑爆上下文，再次触发钩子

回到第 01 步。这一次没人叫停。

01切断源头

错误路径上禁用副作用

一切会再次调用模型的逻辑都停掉。宁可丢掉一次辅助功能，比如自动记忆提取——它不是这轮任务的一部分。

02打断残余

递归深度计数器

检测并打断残余的连锁：已经在恢复里了，就不要再进入恢复。深度是唯一不会说谎的信号。

最后还有一层全局兜底：最大迭代轮数、会话预算上限、连续失败超阈值时升级人工干预—— 单点熔断管单条路径，全局条件管整个会话。
5.1.6 · 实现技巧/五个技巧，两个靶子

五个技巧，只打两个靶子：慢和贵

前面几节描述的工作流程是理想状态。真让它跑起来还要做到三件事——思考质量不降、响应更快、上下文更省。 下面五条就是落地手段，全部来自第二章与第四章的通用技术。

技巧打哪个靶怎么打
并行与流式执行 延迟 参数一完整就开跑，等待被藏进后续的生成过程里。
上下文精细化管理 上下文 文件按行号取片段，命令输出掐头去尾。
环境信息动态注入 上下文 每轮追加一份状态快照，替换掉过时的假设。
终端会话持久化 延迟 不重复 cd、不重复激活虚拟环境。
即时语法反馈 延迟 错误在写入那一刻暴露，省掉一整轮返工。
别当成五个独立开关：第一条改的是执行时序，中间三条改的是上下文里放什么，最后一条改的是反馈回路——它们互相咬合。
5.1.6 · 串行模式/严格的排队

串行的瓶颈不是算得慢，是排队等自己

传统 Agent 是「生成一个工具调用 → 执行完 → 拿结果 → 再决定下一步」。同一条链路上，模型和工具 轮流上班，任何时刻只有一个在干活。

问题留在这里：如果把执行挪进生成的过程里去，这条长条能被压短多少？
5.1.6 · 流式执行/参数完整即启动

第一个调用的参数一完整，就开始跑

不必等整轮生成结束。第一个工具调用的参数一经完整生成并通过校验，立刻启动，与后两个调用的生成过程重叠进行。

5.1.6 · 并发与故障/默认不并发

并行省下的时间，要用边界守住

并发把失败的影响面放大了：一批调用同时在跑，一个炸了，其余的怎么办。答案写进工具定义里。

01声明

并发是一个字段parallel: false

每个工具定义都应写明自己能否并发执行。默认是否——不声明就不并行，这是失败安全的默认值。

02传播

失败沿依赖中止cascade abort

某个调用失败时，级联中止同一批并行启动、且依赖该结果的其他调用，不浪费算力。

03边界

独立调用不连坐

与失败无关的调用照常跑完，发起它们的父级操作也不被终止——中止只沿依赖边传播。

接得上 5.1.4：那一节讲的是「一个失败不该拖垮整批」这条原则，这里看到它的实现形态——一个布尔字段，加一次沿依赖边的传播。
5.1.6 · 上下文/先算一笔账

窗口有百万 token，也不该把仓库塞进去

Coding Agent 的根本矛盾很朴素：代码库通常很大，上下文窗口有限。即使模型号称支持百万级 token， 把整个代码库一股脑塞进去，既不经济，也没必要。

01一个文件

5,000 行 ≈ 6 万 token按每行约 12 token 估算

一个中等大小的源码文件全文读进来，就已经是一次小型对话的量级。

02一个任务

读十来个文件，就是几十万

改一个功能，看十几个文件是常态。还没动第一行代码，窗口先去了一大半。

03一笔账

读进来的每一行，之后每轮都跟着走

一次贪心的全文读取，会在后续每一轮推理里重复计费，直到它被挤出窗口。

所以上下文管理要在多个层面展开：读文件、跑命令、看环境——下面三页，一层一层看。
5.1.6 · 文件读取/按行号取，不读全文

读文件也要有粒度：只要那五十行

对大型文件，工具应支持按行号范围读取；返回时每行以真实行号作前缀。这个设计小到几乎看不见，价值却很大。

READ · 按行号范围取，带行号返回
Agent → read("src/main.py", 100..150) 工具返回： 100| def handle_request(req): 101| token = req.headers["auth"] 102| user = verify(token, cfg) | … （103–141 行省略） 142| return jsonify(resp) # 3,842 行的文件，这次只进来 51 行 Agent → edit("src/main.py:142", …)
  • 只加载要看的那一段。三千多行的文件，没必要为了改一行而整体读进来。
  • 行号是坐标。模型因此能说「src/main.py 第 142 行」——引用没有歧义，后续 edit 才落得准。
  • 省略处要标出来。让模型知道手上是片段，不会误以为文件到此为止。
5.1.6 · 命令输出/前因后果留下，中间不留

终端输出要掐头去尾，全量落到磁盘上

编译或测试可能吐几千行。错误通常在两头：开头是出错的上下文，结尾是总结和退出码。

BASH · 一次失败的测试运行
$ pytest -q tests/ # 1,284 行 FAILED tests/test_api.py::test_rate_limit assert resp.status == 429 AssertionError: 200 != 429 … 中间 1,204 行已省略 … （完整输出 → /tmp/agent/pytest-7f3a.log） ============================= 1 failed, 212 passed in 8.4s
  • 头留上下文。失败发生在哪个用例、断言什么、期望与实际差在哪——这些都在前面。
  • 尾留总结。失败总数、通过总数、耗时，一行就够判断「这次改动是变好还是变坏」。
  • 中间换一行提示。省略多少行、去哪找全文，都写清楚，模型就知道还有后手。
  • 全量落盘，按需再读。真要细节，用上一页的按行号读取，把一小段取回来。
不是新机制：这就是第四章的长输出截断与持久化，在编程场景里最频繁的一次应用。
5.1.6 · 环境感知/每轮一份快照

模型缺的不是更长的提示词，是当前的现场

这是第二章的 Agent 状态栏在编程场景里的集中体现：每次推理前，把环境状态追加在上下文末尾。

AGENT STATUS · 每轮推理前注入
cwd ~/proj/agent-core branch feat/stream-tools ↑2 未推送 commit 3f2a1c9 校验流式参数是否完整 b71d0e4 拆分 tool 定义 9c4a882 给工具加并发标记 dirty M core/stream.py +42 −7 M core/tools.py +18 −3
01cwd

路径不写错

相对路径、模块名、测试路径，全都相对它。

02branch

不以为在 main

分支错了，提交和回滚都会落在错的地方。

03log

知道演化脉络

最近几条提交说明这块代码刚被谁动过、为什么。

04diff

知道改了什么

未暂存与已暂存的差异，决定「改完」还是「还要改」。

四项各堵一个错。这份快照每轮都会变，所以它不能写死在系统提示词里——下一页算这笔账。
5.1.6 · KV Cache/位置决定成本

改一个分支名，整段缓存全废

静态系统提示词是一段稳定前缀。一旦为了塞进「当前分支」去改写它，前缀就变了——缓存整体失效，每轮从头重算。

写法 A追加在末尾

前缀不动，只算增量

状态栏挂在历史消息之后，每轮只为新增的几千 token 付费，前缀始终命中缓存。

写法 B写进系统提示词

前缀一变，全量重算

省了「在哪注入」这点设计，代价是每轮都把十万 token 重新 prefill 一遍。

收一条判断：上下文的结构——什么在前、什么在后——本身就是性能设计，不只是内容设计。
5.1.6 · 状态持久化/终端要一直开着

每条命令一个全新 shell，状态就全丢了

与代码交互的许多操作都依赖环境状态：切换目录、激活虚拟环境、设置环境变量、启动后台服务。 这些东西住在 shell 里，不在文件里。

SHELL · 每次都从零开始
# 会话 A $ cd ~/proj/agent && source .venv/bin/activate $ python -V Python 3.12.4 # 会话 B · 下一条命令，全新 shell $ pwd /home/dev ← 目录回去了 $ python -V Python 3.9.1 ← 虚拟环境没了
  • 状态只在当前会话有效。激活虚拟环境这类操作，效果无法跨会话传递——不是权限问题，是进程边界。
  • 重复劳动还在其次。更贵的是每次都要重新确认「我在哪、用哪个解释器」，而这些信息本来不该重复消耗推理。
  • 所以启动时开一个终端，全程复用。工作目录、环境变量、后台进程都留在里面。
  • 但保留隔离终端。并行任务需要互不干扰的会话——持久化是默认，隔离是能力，不是二选一。
这更符合人的习惯：我们本来就长期开着一个终端窗口，而不是每条命令都新开一个。
5.1.6 · 即时反馈/把 IDE 的红线搬到工具层

写完就检查，别等用户说「跑一下」

文件写入操作一完成，工具层就自动运行对应的 linter 或语法检查器，把结果作为工具返回值的一部分交回去。

WRITE · 返回值里带检查结果
Agent → write("core/stream.py", patch) 工具返回： 已写入 core/stream.py +42 −7 lint · E999 IndentationError line 88 unexpected indent lint · 1 error, 0 warning # 下一轮推理，第一眼就是第 88 行 Agent → edit("core/stream.py:88", …)
  • 不等测试。等到跑测试才发现语法错，中间已经白跑了一整轮推理。
  • 错误带坐标。文件名、行号、错误类型一起回去，模型下一步就能直接改那一行。
  • 就像 IDE 的红线。打错一个括号，编辑器立刻标出来——Agent 也该有同样的即时性。
五条收在一起：并行与流式、上下文管理、环境感知、状态持久化、即时反馈——它们不是孤立的优化点，而是相互配合的设计决策，指向同一件事：让 Agent 像经验丰富的开发者那样流畅地工作。
5.1.1 — 5.1.6/阶段小结

六节讲完，其实是一条因果链

不是因为 Coding 重要才拿它当例子，是因为它同时具备三件事：能造工具、能被验证、有现成的工程基础设施。

ARC 01凭什么

代码是元能力

七个工具里没有「搜索网页」，但会写代码就有了一切：缺什么能力，当场造一个。 通用 Agent 也是把 Coding 当内核，把文件系统当中枢。

5.1.1 · 5.1.2

ARC 02怎么干

先认知，再动手，用测试收口

六个阶段里前三个一行代码都不写：补文档、澄清边界、写一页可被审的设计。 完成的标准不是「代码写完」，是「测试通过」。

5.1.3

ARC 03怎么稳

把判断权交给基础设施

四件组件、四层故障、三级恢复，每条路径都配上限。 这些东西一件都不在模型里——所以换模型，它们仍然成立。

5.1.4 · 5.1.5 · 5.1.6

串起来看：因为代码能造工具，它才接得住开放式任务；因为任务开放，才必须先对齐再动手； 因为动手的次数多了，稳定就只能靠工程，不能靠模型。
5.1.1 — 5.1.6/明天就能动

读完不用等新模型，下周就能动的三件事

三件事都不碰模型、不等版本，改的都是模型外面那一圈——而那一圈本来就是你团队现成的资产。

ACTION 01一小时

给仓库写一份指令文件

技术栈、目录职责、怎么跑测试、哪些目录别碰。 它每次会话自动注入，是最便宜的稳定前缀，也最不容易过期。

ACTION 02半天

把一条口头规范写成规则

TAKEAWAY 01

把四个问题写进工程里：什么算做完、能碰什么、错在哪、怎么退回去。这四件事没有一件属于模型。

TAKEAWAY 02

你团队那套测试、类型、Lint、版本控制，换个使用者（Agent）就能直接复用——这是传统开发者现成的起跑优势。

TAKEAWAY 03

自动化能走到哪一步，取决于验证能不能自动化。凡是「对不对」还得靠人点头的环节，就是吞吐量的天花板。
