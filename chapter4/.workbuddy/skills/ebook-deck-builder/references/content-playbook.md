# 内容手册：怎么让读者看完能掌握 80%

目标读者是**传统开发人员**（会写业务代码，没做过 Agent）。
衡量标准不是"排版好看"，是**合上浏览器还能复述出结论**。

## 一页一个结论

标题写**结论**，不写主题。

| ❌ 主题式 | ✅ 结论式 |
|---|---|
| 七个核心工具 | 工具只有七个，但够用 |
| 三种能力的关系 | 三种能力，一个内核 |
| 代码的意义 | 几乎一切产出最终都落到代码 |
| 文件系统的作用 | 文件系统是最被低估的架构组件 |

判断方法：标题写成一句**能被人反驳的话**。如果没人能反驳，它只是目录。

## 每页的信息配比

```
chip   ：小节号 · 这页在干什么 · 一句话注解      （12 字内）
标题   ：结论，一行或两行                          （≤26 字）
导语   ：这页要解决什么问题                         （≤2 行，60 字）
主体   ：卡片 3 张 / 表格 1 张 / 代码 1 段         （每格 ≤3 行）
补丁   ：边界、反例、注意事项（.note）              （1–2 行）
```

正文一旦超过这个量，读者的注意力会从"理解"切到"读字"。宁可拆页。

**密度下限同样重要。** 主体只有两张卡、又没有 `.note` 时，页面上下各空 150px 以上，
读者会觉得"这页没做完"。补救顺序：补第三条判断 → 加 `.note` 收一句边界 → 换成表格或 `.split`。
**不要用放大字号或加 padding 来填空白**，那是把内容问题伪装成排版问题。

## 必须翻译，不能照搬的四类原文

1. **清单 → 对照表。** 原文列"七个工具"，直接抄就是七行字，读者记不住。改成表格：工具 / 职责 / 为什么不能少。
2. **流程 → 步骤流或图。** 原文用段落描述执行顺序，读者要自己在脑子里画图。你替他画。
3. **取舍 → 单独立页。** 原文说"A 用了 shell + patch，本书选择七个工具"，这句话信息密度极高但没有展开。**这类"为什么是 A 不是 B"必须单独一页**，因为对开发人员来说，取舍比清单更有迁移价值。
4. **实验 → 页内小卡。** 原文的"实验 5-x"不单独占页，压成卡片：目标一句 + 做法一句。保留信息密度，不打断主线。

## 必须保留的"刹车"

作者写"这个判断有边界""这里不适用"的段落，**一个字都不能删**。

省掉的后果很具体：读者会把"Coding 是核心"当成"所有 Agent 都该用 Coding"，然后在做架构决策时踩坑。这类页通常长得不像重点，但它决定读者是"记住结论"还是"用错结论"。

## 术语处理

- 首次出现：中文 + 英文原文 +（一句人话解释）。例：`Harness（智能体的执行外壳——模型之外那套让它可以动手的工程设施）`。
- 第二次及以后：只用其中一个，不要来回切换。
- 全篇统一：不要一处写 `tool use`，一处写 `工具调用`。

## 代码片段规矩

- 8–12 行。超过就砍到骨架，用 `…` 标出省略，并在旁边说明省略了什么。
- 只保留**能体现设计意图**的行。样板代码、import、错误处理全部删掉。
- 左边代码，右边三条"为什么这样写"。右边不是解释语法，是解释**决策**。

## 结尾三张 takeaway 的写法

按这个顺序，不要换：

1. **anchor** — 这件事的本质是什么（一句话能复述）
2. **transfer** — 怎么迁移到你手上的系统（可执行）
3. **next** — 下一步该看/该做什么（有指向）

三张都必须**脱离上下文也成立**。读者截图发群里，别人不看前面的页也能懂。

## 自检：交付前问自己五个问题

1. 随便挑三页，标题连起来读，是不是一段完整的论证？
2. 有没有哪一页，删掉之后读者理解会断？（没有 = 这页是装饰）
3. 有没有哪一页，需要读者先看别的页才看得懂？（有 = 顺序错了）
4. 每个结论后面，有没有"所以呢"的答案？
5. 最后一页的三句话，能不能直接当会议纪要？
