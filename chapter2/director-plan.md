# 《上下文工程》导演策划与知识映射

## 1. 资料依据与范围

主资料：[《AI Agents in Depth》第二章：上下文工程](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter2.md)。已通过 GitHub connector 读取章节正文，文件约 61,756 字符。动画是为零基础观众重新组织的教育表达，不逐段复述原文。

原文覆盖：上下文定义与能力上限；API 消息结构；ReAct/工具循环；KV Cache 与 Prompt Cache；系统提示词、工具定义与提示注入；Agent Skills 渐进式披露；Agent 状态栏；上下文压缩；长上下文中的 Context Rot；分层压缩与子 Agent 上下文隔离。原文还含多项实验、模型协议差异和研究前沿；为了让六分钟影片易于理解，较深的实现细节不铺陈，只保留必要结论。

## 2. 核心观点

**模型决定一般能力，上下文工程决定模型在当前任务中能用上哪些信息，以及这些信息能否被可靠、经济地使用。**

片尾记忆句：**让有用的信息，出现在正确的时刻。**

## 3. 受众与教学目标

受众：不了解 LLM、Agent、token 或 API 的普通观众。影片不要求先学术语。

观众看完后应能：
1. 把上下文理解为模型本轮实际收到的信息，而非只理解成“聊天记录”。
2. 说明 Agent 会让模型请求工具、由框架执行工具、再把结果放回上下文。
3. 解释知识质量、结构、时间位置与任务状态为什么会影响 Agent 表现。
4. 区分按需加载、状态摘要、上下文压缩和模型训练。
5. 认识上下文安全不是只写一条提示词，而要结合工具权限与输入校验。
6. 理解长上下文有容量成本和检索质量风险；压缩需要保留重要事实与来源。

## 4. 原文知识清单

### A. 必须讲清楚的核心

- 上下文是模型在某次决策时实际“看到”的信息总集，包括指令、用户请求、交互历史、工具结果与工具定义。
- 模型通用能力不能替代业务背景、代码结构、团队规则与环境描述。
- Agent API 通常为无状态调用；框架需要构造消息历史。工具调用请求由模型生成，工具本身由框架执行。
- 上下文布局既影响语义理解，也影响推理成本。前缀保持稳定有助于缓存复用；动态信息尽量以追加方式进入后续消息，而不是重写稳定前缀。
- 系统提示词应清楚、有层级、可维护；外部内容可能包含提示注入，不能将其自动提升为可信指令。
- Skills 渐进式披露让技能详细知识按需进入上下文，避免所有说明永久占用窗口。
- 状态栏把当前目标、进度、计数、已验证事实等显式化，减少模型反复从长轨迹推导状态。
- 上下文压缩不是越狠越好：保留决策、约束、失败路径、关键时间和来源；删除低价值噪声。Context Rot（内容装得下但关键内容逐渐难以有效利用）不同于窗口溢出。
- 子 Agent 隔离可以避免把大量探索过程导入主上下文，但委派任务必须自包含、目标明确。

### B. 有助于理解的辅助内容

- 用项目修 Bug 的故事替代抽象 API JSON。
- 用五类信息块解释消息角色与工具定义：系统规则、用户任务、助手行动、工具结果、工具定义。
- 用“一块固定书脊 + 持续追加的读书笔记”解释稳定前缀与轨迹。
- 用“杂乱档案箱 → 当前任务摘要”解释压缩，但明确摘要可能丢信息。
- 用“只给 Skill 目录，需要时再打开手册”解释渐进式披露。

### C. 进阶内容（不在主线展开）

- Chat Template、tokenization 与 Q/K/V 的数学计算。
- 各模型家族对 thinking/reasoning 内容的不同 API 协议。
- KV Cache 编辑与组合等研究前沿。
- 原文六种压缩策略和具体实验数值。
- 多 Agent 系统的完整架构。

## 7. 视觉方案

### 概念比较

- 黑底霓虹赛博朋克：技术感直观，但容易制造装饰噪声，不利于呈现“档案、规则、工作台”的组织隐喻。
- 纯白极简演示：易读但情绪张力较弱，容易像幻灯片。
- **暖纸白 + 森林绿 + 珊瑚红的编辑式动态图形**：兼具可读性与叙事温度，最适合“知识被组织、筛选、流动”的主线，因此选用。

### 设计令牌

- 分辨率：1920×1080，16:9；30 fps。
- 背景：纸白 `#F6F3EA`，深色结尾 `#18302D`，点阵纹理低透明度。
- 主色：森林绿 `#276A57`，表示被整理的有效上下文。
- 辅色：蓝 `#5A7CA8` 表示模型/用户任务；金 `#E7B44E` 表示动态信息或注意点。
- 警示色：珊瑚红 `#D9674E`，仅用于错误、注入风险、缓存失效。
- 字体：优先系统中文黑体族（Windows 微软雅黑/等线、macOS 苹方、Linux Noto Sans CJK）；片中文字 48–88 px 标题，25–34 px 正文，18–24 px 注释。
- 形状：圆角 12–24 px 的卡片、文件夹、信息块、清晰连接线。相同类型保持相同颜色。
- 运动：信息进入时 12–18 帧缓入；关键转折 20–30 帧；不使用随机漂浮与无意义粒子。
- 转场：前一个镜头的“信息块”转化为下一个镜头中的消息卡片；以形状匹配和线条延续为主。
- 字幕：单行或短句，画面底部带轻浅底板；每屏只强调一个认知。
- 片尾：深绿背景，四个工程原则聚合成 Agent 决策窗口，停留在“让有用的信息，出现在正确的时刻”。

## 8. 旁白方向

当前代码版采用中文字幕驱动的动态图形叙事，尚未嵌入实录或 TTS 音轨。建议正式配音采用普通话、沉稳但有好奇心的叙述风格，语速约 220–250 个汉字/分钟，在核心机制前停顿 0.3–0.6 秒。旁白文案详见 storyboard.md 的每镜头讲解字段。

## 9. 技术边界与用词规范

- 不声称上下文能改变模型权重。上下文提供的是推理时的输入信息。
- “KV Cache”指推理过程中对历史 token 的键值状态缓存；跨请求前缀复用在供应商/推理系统语境中常称 Prompt Cache。名称和实际行为按服务商实现有差异。
- “动态信息放末尾”是用于保持静态前缀稳定的常见工程建议，不是所有 API 的无条件规范；应以具体服务接口能力为准。
- 上下文压缩是有损的信息提炼，必须验证摘要是否保留后续决策需要的事实、约束、时间和引用。
- 原文实验中的压缩率和 Token 用量仅属于作者描述的特定设置，不在主动画中作为普遍性能承诺。
- 提示注入防护不只靠文本规则，也要结合工具权限、来源处理、结构校验和应用逻辑。
- 动画里的项目和日志皆为导演创作的虚构示例，不冒充原文实验。
