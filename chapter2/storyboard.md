## 完整旁白文案

### 01–02：定义与问题

“假设你让一个编程 Agent 修复支付回调 Bug。它很快改完代码，却没读项目规范，也没检查重试逻辑。测试发现，同一笔支付可能被处理两次。模型不会自动知道散落在代码库和团队约定里的背景。问题可能不是它不会写代码，而是缺少完成任务所需的上下文。

上下文，就是模型在这一次决策时实际收到的信息。它不只有聊天记录，还包括开发者规则、当前任务、此前的助手行动、工具说明和工具返回的观察。模型提供通用能力，上下文负责提供地图、路况和任务约束。资料多并不自动代表更好，关键是相关信息是否完整、可信、容易找到。”

### 03–05：API、Agent 循环与模板

“常见聊天 API 中，system 放开发者规则，user 放用户任务，assistant 是模型此前的回复或工具调用请求，tool 是框架执行工具后返回的结果。工具定义通常单独放在 tools 字段，并不是第五种消息角色。

模型返回工具调用请求，不代表工具已经执行。框架读取参数、执行工具、把结果通过对应 ID 回填到消息历史，再次调用模型。时间和天气的参数彼此独立时可以并行；如果第二个工具需要第一个工具的结果，就必须串行。每次 API 调用通常都是无状态的，框架必须重新构造足够历史，并设置迭代上限，防止重复调用。

消息对象还不是模型内部处理的普通 JSON。Chat Template 会把角色、内容、边界和工具调用序列化为 token。不同模型的模板和思考内容协议可能不同，不能随意拼接或删除结构标记。”

### 06–08：缓存、提示词、Skills 与安全

“模型处理序列时，会为已经处理的 token 计算并保存注意力所需的 Key 和 Value。满足条件时，新增内容可以复用已有计算。单次生成过程中的 KV Cache，与跨请求复用相同前缀的 Prompt Cache 并非完全相同。把每次变化的时间戳放在系统规则最前面，可能使变化点之后的缓存无法复用。常见做法是保持稳定前缀，把动态状态放到后续消息里，但实际行为取决于具体服务。

系统提示词需要组织目标、流程、业务规则、输出格式和边界，而不是不断追加互相冲突的要求。抽象规则难以说明时，可以给出输入和理想输出作为 Few-shot 示例；工具描述也要准确表达用途、参数和限制。原文消融实验说明组织质量会影响任务表现，但特定实验结果不是所有系统的固定保证。

Skill 把领域流程写成按需加载的说明：先看目录，需要时再打开细节。Skill 不等于工具，也不会自动授予权限。网页或文件可能包含伪装成命令的提示注入，应作为不可信数据处理。安全还依赖最小权限、参数校验、危险操作确认和结果审计。”

### 09–10：状态栏与压缩动机

“多轮执行后，模型可能需要从长历史里重新推断目标、计数、已完成工作和下一步。状态栏把这些信息显式记录下来。它可以由代码确定性更新，也可以由模型整理；无论哪种方式，关键状态都应验证，因为错误状态会误导后续决策。

压缩有三个动机：控制窗口和成本；把原始记录中的结论整理成容易检索的知识；降低模型因上下文将满而提前收尾的风险。上下文溢出是装不下；Context Rot 是装得下，却因内容过长、过杂而难以找到重点。摘要是有损投影，必须保留后续决策需要的事实、约束、失败路径、时间和来源。”

### 11–13：策略、隔离与总结

“原文比较了六种压缩策略：完全不压缩会保留细节，却可能耗尽窗口；逐页摘要容易重复和碎片化；综合摘要能合并信息，但输入过长时可能截断；任务感知压缩结合当前查询和已有信息；带引用摘要为事实保留来源；自适应窗口则在接近阈值后批量压缩。原文特定实验中，任务感知策略显著降低了 token 使用量，但不能将该结果视为普遍保证。

生产系统通常组合多层策略：先限制大工具输出，再删除噪声、微压缩、归档摘要，最后才全量压缩；连续失败时要熔断。另一个办法是让子 Agent 在独立上下文中完成大量探索，只回传路径、结论和证据。隔离可以避免噪声进入主上下文，但子 Agent 不会自动拥有主 Agent 的所有背景，所以委派任务必须自包含、目标明确。

上下文工程的主线是显式管理信息：组织请求结构，保持稳定前缀，清楚表达规则，按需加载技能，显式维护状态，并通过压缩或隔离控制噪声。每次模型做决定前都可以问：它知道规则吗？知道当前状态吗？有相关证据吗？信息是否可信？历史是否已经过长？让有用的信息，出现在正确的时刻。”
